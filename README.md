# Suvex

**一个自治的 AI 安全测试平台** —— 给它一个目标（网站、代码仓库、TCP 服务、
题目附件），它自己规划、调用工具、验证结论，最后交付一份可直接给人看的报告
或 CTF 题解。

```
suvex-api/    后端：Python 3.12 · FastAPI · PostgreSQL 16 · 46,783 行（app/ 下 118 个文件）
suvex-web/    前端：React 19 · TypeScript 6 · Vite 8 · 44,323 行（src/ 下 160 个 .ts/.tsx）
```

> **数字口径**：都是"文件总行数（含空行与注释）"，按换行符计数（与 `wc -l` 等价）。
> 后端 `app/` 的口径不含 `__pycache__/`。写清口径是因为同一份代码在不同口径下
> 能差一万行 —— 而一份"看起来精确"却对不上的数字比"大约四万行"更有害。
>
> ⚠️ 这些数字**会漂**。本 README 每次更正都会重测，但代码在动，文档跟不上
> 是常态。你读到的数字如果与实测对不上，**以实测为准**。

> **契约是唯一事实来源**：[`suvex-web/docs/api-contract.md`](suvex-web/docs/api-contract.md)
> （3,725 行，换行符口径）。前后端只通过它耦合，规矩是「**发现遗漏先改文档再改代码**」。
> 两者放在同一个仓库，就是为了让契约与两侧实现的同步改动落在**同一个提交**里。

## 它解决什么问题

传统扫描器输出的是**漏洞清单**：几百条按规则匹配的结果，其中大量是误报，
而且没人知道哪条真的能打通。人工渗透测试输出的是**结论**，但一个人一周只能
做一两个目标。

Suvex 的取舍是：**让 agent 像人一样去验证**，然后只交付它真的确认过的东西。
所以它的核心不是"扫得更多"，而是三件配套的事：

| 机制 | 解决的问题 |
| --- | --- |
| **执行留痕** | 每一次工具调用、推理、发现都进事件流并落库，报告的每条结论都能追到过程 |
| **证据分级** | 区分"确证"与"启发式"，拿不准的标 `needs_follow_up`，**不把猜测写成结论** |
| **判据可配** | `findVulns`（找漏洞）/ `captureFlag`（夺旗）/ `verifyFix`（验证已修），决定"怎样算成功" |

## 两个入口

### 1. 渗透评估

给一个目标 + 任务背景（测试范围、测试账号、注意事项），产出漏洞报告。
漏洞有完整的处置工作流：状态流转（`new` → `confirmed` → `fixed` → `closed`）、
指派负责人、SLA 修复时限、按类型分组、附件存证、误报标记。

### 2. CTF 夺旗

给题目附件与题面，agent 去解题。解出后交付的是**题解（Writeup）**而不是漏洞报告 ——
因为一次夺旗任务的产物是"怎么想出来的"，不是"哪里有洞"。

> 判据是 `captureFlag` 时，服务端会把 agent 写的报告**重新分节**成题解版式，
> 并把 flag 提到最前面。执行后端的报告标题与分节标题都是写死的渗透口径，
> 所以这一步只能由我们做（详见 `suvex-api/app/scans/writeup.py` 的模块说明）。

## 跑起来

### 后端

```bash
cd suvex-api
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env                 # 然后生成 SUPEX_SECRET_KEY：python -m app.core.crypto
alembic upgrade head
uvicorn app.main:app --reload        # http://127.0.0.1:8000/api/v1/docs
```

### 前端

```bash
cd suvex-web
npm install
npm run dev                          # http://localhost:5173
```

前端默认请求**当前页面的 origin**，由 Vite 的 `server.proxy` 把 `/api`
转发到后端。所以换地址访问、换机器部署都不需要改配置，而且因为是同源请求，
既没有 CORS 问题，Cookie 也一定带得上。

### 一次跑起来（docker compose）

```bash
cd suvex-api && docker compose up --build
```

### CTF 解题能力：2026-10-12 的环境根因整改

一次针对"难题为什么解不出"的实测，把三个**环境层缺口**找了出来并补上。
它们的共同特征是：**看起来像模型能力问题，实际是环境缺东西**。

| 缺口 | 怎么发现的 | 补法 |
| --- | --- | --- |
| **镜像里没有任何 .NET 工具** | 清点镜像：`mono`/`dotnet`/`ILSpy` 全无。而一道已记录的失败题 `[FlareOn3]GUI` 正是 .NET | `mono-runtime` + `mono-devel`（带 `monodis`） |
| **没有 X Server** | 在真实附件上试 `mono GUI.exe`，**崩在 `Application.EnableVisualStyles()`**：`Could not open display` | `xvfb` + `xauth` + `x11-utils` |
| **没有 `numpy`/`scipy`** | 清点：两者都不在，而 crypto/misc 的矩阵、多项式、信号处理都要它们 | pip 装（实测 cp314 有预编译轮子） |

> **为什么 X Server 这条最要紧**：那道题是 WinForms 题，题面写着
> "本题解出相应字符串后请用 flag{} 包裹" —— **解法本来就是"跑起来看它
> 怎么校验"**，跑不起来等于整道题无从下手。而那个报错
> （`TypeInitializationException`）**看起来像程序坏了或 mono 不兼容**，
> 模型因此把它归因成"混淆器导致跑不起来"，转去手工 patch CLR 元数据。
>
> 实测对照：不套 `xvfb-run` 必崩；套上之后 `mono GUI.exe` 进程存活
> （73 MB 内存）、`Xvfb :99` 正常、日志只剩一句无关的 Gtk 主题警告。

同一轮还修了两个**真实缺陷**：

* **`mode` 被静默丢弃**（时序漏洞）：受理时选的 `safe` 会被排队期间
  变更的全局设置覆盖成 `auto` —— 系统替用户做了一个他明确拒绝过的
  **对外提交**，而消耗的是不可再生额度。修法是受理时落**不可变策略快照**；
* **`ReadError` 不在重试列表**：它是"连上了、读响应时断了"，比
  `ConnectError` 更该重试（本地模型长推理下过载很常见）。实测一次
  14 轮的深度分析因它全部作废。

**已解出的题（2026-10-12 实测，`safe` 模式产出候选）**：`easyre` 9 轮、
`RSA5` 9 轮、`reverse1` 32 轮、`[BJDCTF2020]这是base??` 16 轮。

> ⚠️ **这些数字不能读成"成功率提升"**：这 4 道题**没有旧环境基线**
> （改造前没跑过），所以只能说"能解出、且改造没破坏原有能力"。
> 唯一有基线的是 `[FlareOn3]GUI`（改造前 40/80/80 轮均失败），
> 而它**至今仍未解出** —— 改造让它从"没有工具"走到"能 patch 元数据"，
> 但瓶颈变成了混淆器本身。真正的成功率对照实验**还没做**。

## 设计原则

这个项目里反复出现的几条判断标准，写在最前面免得后来者推翻它们：

**1. 宁可少说，不说错的。**
拿不到 flag 就写"本次没有确认到 flag"，而不是猜一个；证据分级里
`ruled_out` 必须附具体反例，"感觉应该没问题"一律记 `needs_follow_up`。

**2. 失败要说人话，并且给出下一步。**
续跑失败不能只说"会话文件已不在" —— 必须补上"请改用「重跑」"。
用户要的是结果，"不能做"本身不解决问题。

**3. 同一件事实只能有一个出处。**
筛选条件、状态流转表、枚举词汇表都只有一份实现。两份口径迟早漂移，
而漂移的症状（"列表 3 条、角标 7 条"）用户无法解释，只能不再相信界面。

**4. 凭据只走环境变量。**
`.env` / `_uploads/` / `_scan_runs/` 全部不入库，见 `.gitignore` 的分节说明。
`_uploads/` 那条尤其重要：附件是**用户上传的业务数据**（内网截图、抓包），
可能含拓扑甚至演示时粘贴过的令牌。

**5. 注释写"为什么"，不写"是什么"。**
代码本身说清了是什么；注释要留下的是**当时的取舍与踩过的坑**。
所以你会看到大量"⚠️ 这里曾经……"的记录 —— 那是给下一个改这段代码的人看的。

**6. 过程性文档不入库 —— 知识要沉淀到代码旁边，不是沉淀到文档里。**

交接文档、代码审查报告、修复工作单这类文件**曾经入过库**，
2026-10-14 已从 git 历史中移除（见 `.gitignore` 的"过程性文档"一节）。
理由不是"它们不好"，而是**它们的保质期与代码不同步**：

| | 代码注释 / README | 交接文档 |
| --- | --- | --- |
| 改动代码时 | 就在旁边，**会被顺手更新** | 没人记得去改 |
| 过期之后 | 编译/测试会暴露矛盾 | 静默变错，且看起来仍像权威 |
| 内容 | 一条可验证的取舍 | 大量"当时的"数字与环境细节 |

这个项目已经吃过一次亏：README 曾写「32,483 行」，而同一时刻
`app/` 实际是 39,163 行 —— 那个数字对不上**任何**口径。
一份"看起来精确却对不上的数字"比"大约四万行"更有害，因为它让人
以为核实过了。

所以那次移除时做了一件比"删文件"更重要的事：**先把文档里的知识
搬到它约束的那段代码旁边**。例如

- 「一次 `ReadError` 作废了 14 轮」→ 写进 `app/settings/models.py`
  里那个 fallback 字段的注释（它正是为此而加的）；
- 「别顺手格式化、制造无关 diff」→ 写进 `suvex-api/pyproject.toml`
  的 ruff `exclude` 注释，以及本节第 7 条。

⚠️ 确实需要交付某份文档时**走交付目录**，不要 `git add -f` 绕开
`.gitignore` —— 那会让这条规则形同虚设。

**7. 不做与本次改动无关的修改。**
`ruff format` 会让整个仓库变红（HEAD 版本与多个未改动文件都过不了），
但项目**只用 `ruff check`**。顺手格式化会产出几十个无关文件的 diff，
把真正的改动淹没在里面 —— 评审时看不出改了什么。
