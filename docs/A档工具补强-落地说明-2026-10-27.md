# A 档工具补强：落地说明（2026-10-27）

> 承接 `docs/五类题型工具补强-盘点与分析-2026-10-27.md`（盘点 + 下载 + 分档建议）。
> 用户拍板选 **A 档**（把已验证可用的一批工具真正装进沙箱镜像）。
> 本文记录**实际装了什么、踩了什么坑、怎么验证的**，以及**没做的事**。

---

## 1. 为什么不是"把包名贴进 Dockerfile"就完了

盘点阶段给出的 30 个项目里，A 档候选有一半在 Kali 容器里**装不上**。
在一次性容器 `suvex-sandbox:latest` 里逐组实测（`_tmp/probe_a_tier_install.sh`、
`probe_a2.sh`、`probe_a3.sh`）后定下的判据是：

**跑得起来才算数**（本项目对"假工具"的洁癖：装上但一跑就崩，比没装更坏）。

实测结论（这些直接决定了 Dockerfile 的写法）：

| 项目 | 实测结果 | 处理 |
|---|---|---|
| `ropper` | Kali 的 python3 已是 3.14，它依赖的 `filebytes` 用了 Py3.12 移除的 `ast.Str`，**装上即崩** | ❌ 不装 |
| `zsteg` | Ruby gem，依赖链（`rmagick` 等）在离线容器里取不到 | ❌ 不装（`stegoveritas -bruteLSB` 顶替） |
| `semgrep` | Kali 源里没有（`pkg.kali.org` 404），且运行时默认联网拉规则，而容器是 `--network none` | ❌ 不装 |
| `sstimap` | 它的 requirements 把 `requests` 钉在 2022 年的 `~=2.27.1`，直接装会把主 venv 的 requests 降级 | ✅ 放进**独立 venv** `/opt/venvs/sstimap` |
| `github.com` / `npmjs.org` / `rubygems.org` 直连 | 全部 `SSL_EOF_WHILE_READING`（容器网络受限） | ✅ 走 **vendor/ 目录随包分发**（39.9 MB） |

## 2. 实际装进去了什么

镜像 `suvex-sandbox`（= 平台默认的 base profile，artifact/misc/web 类题都用它）新增 14 个命令：

| 命令 | 用途 | 来源 |
|---|---|---|
| `qrencode` / `zbarimg` | 生成 / 解码二维码、条码 | apt `qrencode`、`zbar-tools` |
| `unrar` | 解 rar（比 7z 对加密 rar 稳） | apt `unrar-free` |
| `testdisk` | 分区表扫描/修复 | apt `testdisk` |
| `foremost` | **文件雕复/恢复**（按文件头捞被删文件） | apt `foremost` |
| `vol` | 内存取证（volatility3） | pip `volatility3` |
| `fenjing` | Jinja2 SSTI 自动构造/绕过 | pip `fenjing` |
| `stegoveritas` | 一站式隐写分析（含 `-bruteLSB`） | pip `stegoveritas` |
| `sstimap` | 服务端模板注入扫描/利用 | 独立 venv（vendor 源码） |
| `jwt_tool` | JWT 改算法/爆破/伪造 | vendor 源码 + 主 venv 依赖 |
| `bkcrack` | zip 的 Biham-Kocher 已知明文攻击 | vendor 源码，cmake 现场编译 |
| `pcapfix` | 修复损坏/截断的 pcap | vendor 源码，make 现场编译 |
| `repak` | UE4/UE5 `.pak`/`.utoc`/`.ucas` 解包 | vendor（Rust 预编译二进制） |
| `nuclei` | 模板化漏洞扫描（原本已有，本次纳入自检） | 既有 |

**体积**：`4.34 GB → 4.47 GB`（**+130 MB**）。

## 3. 三个真实的坑（都写进了 Dockerfile 注释）

1. **`prune` 把构建缓存清空了**，导致第一次构建从头跑了一遍 40 分钟的 pip/cmake。
   → 教训：清理磁盘（当时可用只剩 7.5 GB）和"马上要构建"是冲突的，先构建再清。
2. **`jwt_tool` 无参时会打 banner 然后 `sys.exit(1)`**，而 `jwt_tool | head -3`
   在 `set -o pipefail` 下直接判红（退出码 120）。
   → 自检改成"落地到文件再看文本"，判据是"它能打出自己的 banner"。
   `bkcrack` 无参也是非零退出，同一个坑，同样处理。
3. **`photorec` 在 Kali 里根本不存在**。我原以为"Debian 的 testdisk 包顺带装 photorec"，
   实测 `dpkg -L testdisk` 只列出 `/usr/bin/testdisk`，`apt-cache policy photorec`
   的 Candidate 是 `(none)`。
   → 改用 Kali 源里有的 `foremost`（1.5.7-12+b1）做文件雕复，并在提示词里**明写
   "photorec 不在镜像里，用 foremost"**，避免模型去敲一个不存在的命令。

## 4. 关键一步：让模型知道这些工具存在

**装进镜像 ≠ 模型会用。** 这是本项目已经踩过的坑（`browser` 工具当年做进内核，
但 `tools.py` 和 `kernel_system.md` 都没提它，等于装了个没人知道的东西）。

所以同步改了 `suvex-api/prompts/kernel_system.md` §6「先用现成工具」：新增一张
**场景 → 命令**表（二维码、加密 zip 已知明文、坏 pcap、UE4/UE5 包、内存镜像、
Jinja2 SSTI、隐写、SSTI 扫描、JWT、分区/文件恢复），并写明表头那句是**事实断言**：
「下面这批工具镜像里都真装了（2026-10-27 实测过能跑）」。

并加了一条守卫测试把这个断言钉住（见下节）。

## 5. 守卫测试（新增 1 条 + 变异验证）

`suvex-api/tests/test_prompt_tool_names.py` 新增
`test_advertised_misc_tools_are_installed_in_the_dockerfile`：

- **判据**：`kernel_system.md` 里点名的那 12 个命令 → 去 Dockerfile 里查它对应的包名。
  少一个就红，报错直接说缺哪个包。
- **为什么是对账而不是名单**：与 `test_real_skills_no_skill_for_uninstalled_tools`
  同源教训 —— 黑名单会过期，只有"Dockerfile 是唯一事实源"才不会漂移。
- **反向断言**：如果表里某工具在提示词里已经不存在了，也红（防止测试在守一个
  已经不存在的事实）。

**变异验证（2/2 变红）**：
```
[基线] PASS
[变异1-把 repak 的包名改成 repak-does-not-exist] 如期变红
[变异2-声称一个提示词里没有的工具]                 如期变红
[复原] PASS
```

## 6. 镜像切换与部署（Kali）

```bash
docker tag suvex-sandbox:latest     suvex-sandbox:pre-a-tier   # 回滚点（f3fa2656169c, 4.34GB）
docker tag suvex-sandbox:a-tier     suvex-sandbox:latest       # 新镜像（544216f3a5c9, 4.47GB）
```

源码同步用 `rsync -a --delete`（备份在 `/root/suvex/backup-atier-20261027-150149/`），
**顺带删掉了 Kali 上的 `app/kernel/rea.py`** —— 那是上一轮评估后决定不装的 REA 残留，
它在 Kali 上被注册成了 `rea` 工具（`runner.py` 的 `TOOL_NAMES` 第 13 项 + dispatch 分支），
而镜像里没有 `/opt/rea`，属于**活的假工具**（一调必报错）。本地已同步删除
`app/kernel/rea.py` 与 `tests/kernel/test_rea_tool.py`，工具目录回到 **13 个**。

## 7. 真机 e2e：给模型一张二维码图片

光验证"命令存在"不够（本项目吃过亏）。做了一次端到端：

1. 用镜像里的 `qrencode` 生成一张二维码，内容 `flag{atier_qr_ok}`（288 字节 PNG）；
2. 通过产品 API 上传 → 建扫描（artifact + captureFlag）；
3. 观察模型怎么解。

**结果**（`scan_01M5ZC079EK327M779ZJ4Z2WPE`，88 秒，17 轮，31 次工具调用）：

- 第一条命令就是 `command -v zbarimg qrencode python3` —— **说明提示词那张表被读到了**；
- `zbarimg` 被用 **9 次**，`qrencode` 4 次；
- 模型不仅解出，还做了三重独立验证：`zbarimg --raw | od -c` 逐字节核对、
  `pyzbar` 交叉验证、把 21×21 模块矩阵与 `qrencode` 重编码结果**逐位比对（diff=0）**；
- 产出 1 条 finding，`detail_evidence` 里就是 `QR-Code:flag{atier_qr_ok}`。

⚠️ 注意：这条扫描的 `scans.flag` 是 `NULL`，**这不是 bug**。
`app/scans/agent_runner.py:18-19` 写明扫描路径的判据在 v0.64 已从"拿到 flag"
改成"已验证的发现"，`:1052` 注明扫描路径不写 `candidates`（flag 只有 CTF2 解题路径才写）。
答案以 finding 的形式呈现（用户看到的「证据」栏里就有 flag 原文）。

## 8. 没做的事（诚实边界）

- **`suvex-sandbox-re` / `-ir` 两个镜像仍是旧版**：A 档只加进了 base（`suvex-sandbox`）。
  逆向题走 `-re`，若要用 `repak`（UE5）等还需单独构建一次 `-re`。
- **`semgrep` / `ropper` / `zsteg` 明确不装**，理由见 §1，已写进提示词让模型别调。
- **`photorec` 不可用**（Kali 无此包），用 `foremost` 顶替。
- **B 档 / C 档未动**（B 档要装的动西更大，C 档不建议装）。
