# v1.21 验收报告：附件条即发即收 + 截断续跑独立预算

用户报的两个缺陷（原话）：

1. 「对话发送了文件还贴在这」
2. 「解一半又停下了」

## 一、缺陷 1：附件条挂到整轮结束

- 根因：`suvex-web/src/data/chat.ts` 的 `sendMessage` 里，清空 `stagedAttachments`
  写在 `await streamTurn(...)` **成功之后**。整轮跑多久，附件条就在输入框上方挂
  多久；而这段时间输入框已经切成「插话」模式，那条残留看起来像"下次发送还会带上"。
- 修法：按**发送那一刻**就收起；失败/异常时**有条件**放回。
- 放回的前置条件（自己第一版漏的）：后端 `run_turn` 一进来就
  `attachments.hand_over()`，把暂存文件**搬**到会话交接目录。所以只要这一轮真的
  开始跑了，把 chip 放回去会让下一条消息带一个服务端查不到的 id → 附件静默丢失。
  判据用 `pendingUserContent`（发送时写、收到第一条 user 帧时清）。

## 二、缺陷 2：「解一半又停下」

- 根因（DB 实证，会话 `chat_01M60YNRTZ0Z8S7BF85NNWMRNN`）：三条 `chat_turn_runs`
  全部 `nudges_used=2` 就收尾；`chat_messages` 末尾正文停在「第二次 `read` 则」。
  模型把推理写进正文、反复撞 `max_tokens`，而旧 `nudge.should_nudge` 把"格式错"
  与"被截断"共用 2 次预算，第三次被切断时什么都不做。
- 修法：
  - `suvex-api/app/chat/nudge.py` 新增 `truncations_used / max_truncations`，
    截断分支提到格式预算**之前**；
  - `suvex-api/app/chat/engine.py` 新增 `MAX_TRUNCATION_CONTINUES = 6`、
    `CHAT_MAX_TOKENS = 8192`（默认 4096 太小），两个循环分别维护
    `nudges_used`（总数）与 `truncations_used`（子集）；
  - `chat_turn_runs.truncations_used` 落库 + 迁移 `e8b4c1f60a72`，接手时接着用同一额度。
