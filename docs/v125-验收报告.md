# v1.25 验收报告：对话页重设计（过程面/交付面分离 + 中断控制 + 放宽轮次预算）

## 用户诉求

1. 「打断当前会话也没做，看人家 CyberStrikeAI 的设计」
2. 「又中断了，就不能一次性把 flag 给我解出来吗，能不能重新设计我的对话页面功能」

## 一、过程面 / 交付面分离

对齐 CyberStrikeAI 的 `docs/zh-CN/agent-finalization-best-practices.md`：
**过程面与交付面必须隔离** —— 只有过 final gate 的内容才写 `messages.content`，
其余进 `process_details` 时间线。

实现：
- 新列 `chat_messages.surface`（`answer` / `process`），迁移 `a3c7e91d4f28`。
- 引擎：**带 ACTION 的旁白**落 `process`；工具结果一律 `process`；
  只有真正给出结论的那条落 `answer`。轮末 `_collapse_turn_answers` 保证
  **一轮只有最后一条 assistant 是 `answer`**。
- 前端 `groupMessageRows`：连续旁白折成一个「过程详情 · N 步」折叠块。
  **工具行留在主线**（本来就是一行灰字）—— 再折一层等于黑箱，
  "看不到它在干嘛"比"气泡多"更糟。
- 中断时注入的说明是 `process` 的 user 消息（不冒充用户自己打的字，
  与 CyberStrikeAI 的 `contextInjection:false` 同口径）。

实测（会话 `chat_01M61Q1SPG1EHETKGXBQXHJYW9`）：
`answer_bubbles = 1`、`process_groups = 1`。DB 侧：
seq2 旁白=`process`，seq3 工具=`process`，最终答复=`answer`。

修过的两个现场缺陷：
- 「两条几乎一样的结论气泡」→ 轮末 collapse（`d3810584`）+ 轮末无条件重取
  服务端消息（`258c61ce`，因为降级发生在流式推送之后，界面需以服务端为准）。
- 判据**不收紧**（"像不像半句"不可靠：`pwd` 输出是 `/work`。18 字完整回答
  任何启发式都会误判），宁可多问一次模型，也不放行一次半路停。

## 二、中断控制（对齐其「中断当前步骤」弹窗）

- `app/chat/interrupts.py`：进程内跨线程信号（单 worker 前提，与 sandbox 同）。
- 检查点：流式输出**每个增量**查一次（立刻停）；**工具执行中打断不了**，
  等它返回才生效 —— 弹窗里明写这一点（不说实话用户会以为点了没反应）。
- `POST /chat/sessions/{id}/interrupt` `{mode: continue|stop, note?}`；
  没有 open 轮次 → `409 NO_RUNNING_TURN`。
- `continue`：停 → 注入 `INTERRUPT_NOTE`（process）→ 自动接着跑。
- `stop`：本轮结束，执行记录落新增状态 `cancelled`（迁移 `b8d3f52a67e1`
  手写 CHECK —— autogenerate 不比对 CHECK）。不落 `interrupted` 是因为那会
  被后台 resumer 自动接手，与"别再跑"相反。
- 前端：当前会话在跑时出现「中断」按钮 → 弹窗（说明 textarea + 关闭 /
  彻底停止 / 中断并继续）。

实测：`interrupt_button_visible=true`，弹窗三件齐全；
「中断并继续」后弹窗关闭、这一轮继续并产出结论；
「彻底停止」后 `chat_turn_runs.status = cancelled`、界面退出 running。

## 三、不再"解一半停"

- `MAX_TOOL_ROUNDS` 6 → **40**、`MAX_TOOL_NUDGES` 8 → **30**。
  一个 pwn 题从侦察到拿 flag 通常十几到几十轮工具往返，6 轮上限
  本身就是"必然半路停"。
