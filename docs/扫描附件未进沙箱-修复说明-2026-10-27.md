# 扫描路径「题目附件从未进沙箱」修复说明

日期：2026-10-27
触发场景：用户要把 97 MB 的 `千千的咲.zip` 传到 Suvex 解题。

## 一、怎么发现的

用户把附件上传后，扫描跑起来了、容器也起来了、状态是 `running`，
但进容器一看：

```
$ docker exec suvex-scan-E31P21DZG5B0 ls -la /work
drwxr-xr-x 3 solver solver 60 ... .
drwxr-xr-x 1 root   root   4096 ...
drwxr-xr-x 2 solver solver 40 ... persist      ← 只有这一个空目录

$ docker exec suvex-scan-E31P21DZG5B0 ls -la /work/attachments
ls: cannot access '/work/attachments': No such file or directory
```

宿主侧文件明明在：
```
$ ls -l /root/suvex/suvex-api/_scan_runs/scan_01M5YTH6KXCFV3E31P21DZG5B0/challenge/
-rw-r--r-- 1 root root 105774224  千千的咲.apk
```

而同一时刻模型在 `scan.log` 里的原话是：

```
[reasoning] The environment is empty. No attachments, no challenge dir access.
            The problem says "本题没有附件".
[reasoning] The platform itself confirms **"可用附件：（无附件）"**
```

然后它把剩下的 348 轮全花在 `grep -rI / ... flag{` 盲搜整个文件系统、
甚至跑去 `ctf2.dasctf.com` 找题目文件上。

**它不是不会解，是没题可解。**

## 二、根因：两处接线都断了

`uploads.claim()` 把（解包后的）题目素材铺在 `challenge_dir(scan_id)`，
即 `_scan_runs/<scan_id>/challenge/`。但扫描路径起沙箱时：

### 断点 1 —— 没挂载（`app/scans/agent_runner.py`）

```python
sandbox = ctf2_runner.SandboxContainer(
    name=sandbox_name,
    image=...,
    network_name=ctf2_runner.PENTEST_NETWORK,
    cpus=..., memory_mb=...,
    workspace_dir=spec.run_dir / "agent_run" / "workspace",
    volume_write=...,
)          # ← 缺 attachments_dir，走默认 None
```

`SandboxContainer._argv` 里那条 `-v <dir>:/work/attachments:ro`
只在 `attachments_dir is not None and .is_dir()` 时才生成，所以从不生成。

对照：**CFT2 解题路径是对的**（`app/kernel/runner.py:8262` 有
`attachments_dir=_attachment_dir(challenge_id)`）。也就是说这个洞只存在于
**扫描**路径。

### 断点 2 —— 附件清单写死为空（同一文件）

```python
return ctf2_runner.SolveSpec(
    ...
    attachments=(),        # ← 写死
    ...
)
```

空元组有两个后果：
1. `_tool_read_attachment` 在 `spec.attachments` 里按名字找 → 无论传什么
   名字都回「没有这个附件」（连列都列不出来）；
2. `_initial_prompt` 的 `if spec.attachments:` 不成立 → 「## 附件」整段
   不出现在提示词里 —— 模型根本不知道 `/work/attachments` 该有东西。

两处一起，才解释得通「平台自己都说无附件」。

## 三、影响面（要说准确）

- **受影响的**：所有 `targetKind=artifact` 的扫描（纯附件逆向 / Misc 题）。
  这类题的全部信息都在附件里，附件没进沙箱 = 100% 白跑。
- **不受影响的**：CTF2 解题路径（一直是对的）；`url`/`service` 目标
  （它们的题目不在附件里）。

## 四、修法

`app/scans/agent_runner.py` 三处改动：

1. 新增 `_scan_attachments(scan_id) -> tuple[Path, ...]`：
   列出 `challenge_dir(scan_id)` 下的普通文件（跳过目录与隐藏文件，与
   `scans.runner._workspace_files` 同一口径）；目录不存在时返回空元组。
2. `SandboxContainer(...)` 补 `attachments_dir=challenge_dir(spec.scan_id)`。
3. `SolveSpec(...)` 的 `attachments=()` 改为 `attachments=_scan_attachments(spec.scan_id)`。

## 五、验证（真机，不是单测）

### 5.1 挂载真的出现了

```
$ docker inspect suvex-scan-0332839NSJVG --format '{{range .Mounts}}{{.Source}} -> {{.Destination}} rw={{.RW}}{{end}}'
/root/suvex/suvex-api/_scan_runs/scan_01M5YXF01Z6EYT0332839NSJVG/challenge -> /work/attachments rw=false
/var/lib/docker/volumes/e9f6018e.../_data -> /opt/host-resources rw=true

$ docker exec suvex-scan-0332839NSJVG ls -la /work/attachments
-rw-r--r-- 1 root root 105774224  千千的咲.apk
```

### 5.2 模型行为翻转（同一道题，前后对照）

| | 修复前 | 修复后 |
|---|---|---|
| 第一轮工具调用 | `grep -rI / --include=* flag{` 盲搜根目录 | `ls -la /work/attachments/ && file /work/attachments/*` |
| 日志里「没有附件/无附件」出现次数 | 多次 | **0 次** |
| 读 `/work/attachments` 次数 | 0 | **5 次** |
| 实际动作 | 声称题目无附件，去平台 API 找题目文件 | 解包 APK → 发现 `main.obb.png` 是 ZIP → 解开 UE5 IoStore → 分析 `.pak`/`.utoc`/`.ucas`，尝试 `libUnreal.so` 的 Oodle 解压 |
| 工具调用数 / 时长 | 白搜（348 轮空转） | **380 次 / 2405 秒，全程在解真题** |

### 5.3 诚实的边界：它没解出 flag

最终 `status=completed`，`flag=None`，`findings={'info': 3}`。

原因不是修复没生效，而是**这道题本身超出了当前镜像能力**：
flag 藏在 UE5 IoStore（`.ucas`）里，压缩算法是 **Oodle**（私有编解码器，
需要 Unreal SDK 的 `OodleLZ_Decompress`）。镜像里没有，模型反复尝试
`nm -D libUnreal.so | grep -i oodle` 也确认了这一点。

这条要说清楚：**附件送达链修好了，是这道题的解题链还缺 Oodle 支持。**

## 六、守卫测试

`suvex-api/tests/test_scan_attachments_reach_sandbox.py`（6 项，全绿）：

| 测试 | 防的是什么 |
|---|---|
| `test_challenge_dir_is_what_claim_writes_to` | 前提：`challenge_dir()` 仍指向 `claim()` 铺素材的目录（路径口径变了会让下面几条指错地方却仍通过） |
| `test_sandbox_mounts_the_challenge_folder_read_only` | 附件目录必须以 `:ro` 挂到 `/work/attachments` |
| `test_no_attachment_dir_means_no_mount` | 反面对照：没附件时不挂不存在的路径（否则 docker 直接起不来） |
| `test_solve_spec_attachments_lists_real_files` | `_scan_attachments()` 只列普通文件，跳过目录/隐藏文件 |
| `test_scan_attachments_is_empty_when_folder_is_missing` | 目录不存在 → 空元组，不报错 |
| `test_engine_wires_the_mount_and_the_list` | 静态守卫：`_run_engine` 与 `build_solve_spec_from_scan` 里那两行接线还在 |

**变异验证**（`_tmp/mutate_attachments.py`，两式都 RED）：

```
[基线] exit=0
[变异] 撤回挂载（删掉 attachments_dir 那一行）        → exit=1  FAILED test_engine_wires_the_mount_and_the_list
[变异] 撤回清单（把 _scan_attachments 换回空元组）    → exit=1  FAILED test_engine_wires_the_mount_and_the_list
✅ 两处变异都被抓住了
```

⚠️ **这条要诚实说**：两式变异都只让**静态断言**变红，行为断言
（挂载 argv / 附件清单）没变红。原因是行为测试里我自己构造
`SandboxContainer`，没有真正走 `_run_engine`（那个函数要起真 docker
容器 + LLM 网关，单测跑不动）。所以：
- 行为测试证明的是 `SandboxContainer` **本身**没问题；
- 真正盯着 `_run_engine` 接线的是那条静态守卫。
