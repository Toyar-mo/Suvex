## 二、五处"说反话"（真 bug，已修复）

这五条的共同特征是：**界面写 A，代码做 B**，且方向相反。用户会按文案形成错误认知，
出事时无从排查。它们比"缺功能"严重——缺功能用户会发现，说反话不会。

### 1. 「禁止沙箱访问外网」——说会失败，实际强制开网 🔴

- **旧文案**：`限制影响范围，但针对外部目标的扫描会直接失败 —— 按需开启。`
  以及开关打开后的警告块：`针对 https:// 目标的动态扫描将无法执行，只能分析本地代码。`
- **代码实际**（`app/scans/agent_runner.py:1137`）：
  ```python
  is_network_target = spec.target_kind in ("url", "service")
  network_isolated = bool(spec.sandbox_network_isolated) and not is_network_target
  ```
  即：`url` / `service` 形态**强制开网**，设置值被忽略。
- **为什么代码是对的**：这段代码上方有长注释说明——曾经漏了这道判断，导致一次 web 渗透被关进
  `--network none`，镜像里 98 个工具（nmap/ffuf/gobuster/sqlmap）全连不上，96% 的动作退化成
  宿主侧逐个猜 URL。所以"强制开网"是修复，不是 bug。
- **危害**：用户以为开了这个开关就隔离了外部扫描；实际对网络目标毫无作用。他既高估了安全性，
  又会在扫描正常跑完时以为"隔离没生效"。
- **已修**：标签改为「禁止沙箱访问外网（仅本地代码目标）」，hint 与警告块写明
  `url`/`service` 会**强制开网**，并注明出站边界仍由宿主机 iptables 白名单收窄。
  文件：`suvex-web/src/components/settings/SandboxPanel.tsx`

### 2. 「发现严重问题时立即通知」——承诺实时，实际从不触发 🔴

- **旧文案**：`不等扫描结束，边跑边发 —— 早一分钟知道就少一分钟暴露窗口。`
- **代码实际**：`notify_on_critical_immediate` 在 `app/settings/` 之外**零消费端**：
  ```
  app/settings/models.py:198   定义
  app/settings/router.py:431   回显
  app/settings/router.py:580   回显
  app/settings/router.py:614   写回
  ```
  唯一的业务判断函数 `dispatch.should_notify` 自己在注释里写着：
  > `这个开关在扫描结束时没有作用 —— 它的意思是在扫描过程中发现严重漏洞就立刻发。本轮只在收尾投递，所以它不影响这里的判断。`

  投递入口只有 `app/scans/scheduler.py:476`，在**扫描收尾**时调用。全库没有扫描中途投递的路径。
- **危害**：这是告警通道。用户以为自己拿到了实时告警，实际一个字节都不会发。他会在真正的
  严重漏洞出现时认为"没触发说明没严重问题"——**沉默被他解读为安全**，这是最坏的失效方向。
- **已修**：hint 改为明确说明当前版本不生效、值会保存但无投递路径读它。
  文件：`suvex-web/src/components/settings/NotifyPanel.tsx`

### 3. 「发送测试消息」——说不会真发，实际会真发 🔴

- **旧文案**：按钮 `title="当前只校验地址形状，不会真的发送"`，
  旁边说明 `接口只做本地校验 —— 点它不会真的发出通知`。
- **代码实际**（`app/settings/router.py:695` 起 `test_channel`）：
  docstring 第一句就是 **「## v0.89：这一步已经**真的发**了」**，流程是
  `形状校验 → 真发一次（dispatch.dispatch_one）→ 按真实结果写 verified / verifyError`。
  只有邮件（SMTP）仍未接入，且会明确返回原因。
- **危害**：方向与上一条相反但同样危险。用户以为点"测试"是安全的本地检查，实际一条
  真实消息会到达他的 Slack / 工单系统。在工单系统里这会产生一条噪音工单；
  更糟的是有人会因为这个错误认知而不敢测、或测了之后误以为配置没问题。
- **已修**：`title` 改为「会对 Webhook / Slack 真的发一条测试消息；邮件尚未接入」，
  按钮旁说明改为「Webhook / Slack 会真的收到一条测试消息；邮件渠道暂不支持」。
  同时修正了 `data/settings-store.ts` 里"`verified` 恒为 false、成功分支走不到"的过时注释
  ——那段话会让维护者以为成功分支是死代码。

### 4. 「扫描结束时通知」——说"没发现问题也发"，默认配置下不发 🔴

- **旧文案**（`NotifyPanel.tsx`「扫描结束时通知」的 hint）：
  「即使没有发现问题也发一条，用于确认扫描确实跑完了。」
- **代码实际**：`dispatch.should_notify` 里 `notify_on_scan_complete` **不是**最后一道
  判据，后面还有一层 `_passes_severity`：

  ```
  app/settings/dispatch.py:97   _SEVERITY_RANK = {info:0, low:1, medium:2, high:3, critical:4}
  app/settings/dispatch.py:281  rank      = _SEVERITY_RANK.get(severity)
  app/settings/dispatch.py:282  threshold = _SEVERITY_RANK.get(min_severity)
  app/settings/dispatch.py:285  return rank >= threshold
  ```

  而干净扫描的 severity 由 `app/scans/scheduler.py:518` 起的 for/else 决定 ——
  findings 计数全 0 时四个档都没命中，else 分支落到
  `app/scans/scheduler.py:523` `severity = Severity.INFO.value`（rank **0**）；
  默认 `app/settings/models.py:192-194` 的 `min_severity` 列
  `default=Severity.HIGH.value`（rank **3**）。
  `0 >= 3` 为假 ⇒ **不发**。
  （`notify_on_scan_complete` 那道判断在 `dispatch.py:308`，`_passes_severity` 在
  `dispatch.py:311` —— 阈值这一层在开关**之后**，所以开关拦不住它。）
- **行为实测**（`_tmp/er/probe_clean_scan_notice.py`，跑真实 `should_notify`）：

  | 阈值 | 干净扫描（severity=info） | 有高危（severity=high） |
  |---|---|---|
  | info | ✅ 发 | ✅ 发 |
  | low | ❌ 不发 | ✅ 发 |
  | medium | ❌ 不发 | ✅ 发 |
  | **high（默认）** | ❌ **不发** | ✅ 发 |
  | critical | ❌ 不发 | ❌ 不发（high 不够格） |

  即：**只有阈值选到「信息」时**这句话才成立。（顺带印证了 `_passes_severity`
  对未知/不够格值一律不放行的取向 —— critical 档下连 high 也拦。）
- **危害**：这条在四者中后果最直接。用户打开「扫描结束时通知」的**全部目的**就是
  "确认扫描确实跑完了"；默认配置下他恰恰拿不到这个回执，而**沉默会被读成"没扫完"**，
  于是去怀疑调度、去重跑 —— 一个纯文案错误转成了一个假的故障信号。
- **已修**：hint 改为按当前阈值分两种说法 ——
  阈值=`info` 时说「包括没有发现任何问题的情况（阈值已选到「信息」）」；
  否则说「仍受上面的阈值约束……想每次都收到回执，把阈值选到「信息」」。
  文案随 `draft.minSeverity` 实时变化，不需要用户自己推理两者关系。

### 5. 「归档产物保留期」——说 challenge 目录不受影响，实际会一起删 🔴

- **旧文案**（`ScanRetentionPanel.tsx:182`「归档产物保留期」的 help）：
  「产物目录（扫描日志、报告素材）再留这么多天就清理掉，释放磁盘。
  **附件原件与 challenge 目录不受影响。**填 0 表示不自动清理。」
- **代码实际**：`challenge/` **就在**要被删掉的那个目录里面 ——

  ```
  app/scans/runner.py:503   return get_settings().scan_root / scan_id / CHALLENGE_DIRNAME
  app/scans/runner.py:557   shutil.rmtree(target, ignore_errors=True)   # target = scan_root/<scan_id>
  ```

  调用链：`service.sweep_retention`（`app/scans/service.py:2113-2115`）
  → `runner.sweep_retired_artifacts(db, retention_days=...)`
  → `remove_scan_artifacts(scan_id)` → 整个 `<scan_id>/` 被 rmtree，
  `challenge/` 是它下面的子目录，**跟着一起没了**。
- **代码注释其实一直是对的**：`runner.py:715-718` 明确写着
  「⚠️ 特别注意 `challenge/` 目录……**跟着产物一起删是对的**（它是派生物，
  从 `_uploads/` 的原件还能再生成）。而 `_uploads/<scan_id>/` 是**另一个路径**，
  按 id 拼路径从构造上就碰不到它。」—— 是界面文案把这句话写反了。
- **危害**：这是五处里唯一**指向不可逆操作**的一条。清理本身不可逆，
  用户读到"challenge 目录不受影响"才敢打开它；打开之后他的题目素材没了，
  而界面上找不到任何提示。注释里那句"否则用户会以为它连附件一起删，
  从而不敢开启"（`ScanRetentionPanel.tsx:176-177`）说明作者正是想避免
  这个后果 —— 但写出来的句子恰好制造了相反的误解。
  另外 `runner.py:502` 还留着「`sweep_retention` 至今不删任何目录」的
  过时说法（该能力已在 2026-10-16 补上），也应视为同源的历史残留。
- **已修**：help 改为「产物目录（扫描日志、报告素材、**challenge/ 里解开的
  题目素材**）……**附件原件不受影响——它在 `_uploads/` 下，重跑同一道题还要用**」。
  把"删什么"列全、把"留什么"指到具体路径，而不是笼统的"不受影响"。

## 三、死代码（已清除）
### `BACKEND_PENDING` 三件套 + 永久不可达分支

```ts
export const BACKEND_PENDING = { sandbox: false, notices: false } as const
export const HAS_PENDING_BLOCK = Object.values(BACKEND_PENDING).some(Boolean)  // 恒 false
export const BACKEND_PENDING_NOTE = '…'                                        // 无引用
```

- `HAS_PENDING_BLOCK`：**0 处外部引用**
- `BACKEND_PENDING_NOTE`：仅出现在两处"这里原来挂着它"的注释里，代码无引用
- 唯一真消费方 `SettingsPage.tsx` 的
  `{(BACKEND_PENDING.sandbox || BACKEND_PENDING.notices) && (…)}` —— 永远为 `false`，**不可达**

**为什么该删而不是留着**：这段代码自己的注释写明了规矩——"已交付却还标着未交付 = 否认一个
已经可靠的功能"。一个永远不渲染、但看起来在待命的提示条，会让下一个维护者以为某块仍未交付。
**规矩留下（已改写为文档注释），代码不必留下。**

顺带修正：`DataBoundaryNote` 的"已接入服务端"清单漏了沙箱与通知（它们早已持久化），
补全为「模型服务、沙箱与执行、通知规则与渠道、扫描保留、访问令牌与登录口令」。

## 七、遗留建议（未改，需产品决定）

1. **`notify_on_critical_immediate` 要么实现、要么下掉。** 目前文案已如实标注"不生效"，
   但一个能保存、能回显、却不产生任何行为的告警开关，长期看仍是负债。实现扫描中途投递
   需要 `dispatch` 在发现严重漏洞时被调用一次，属于独立一块工作。
2. **沙箱面板的"仅自研引擎生效"标注**是本次补的（`timeout_seconds` / `allow_volume_write`
   只有自研引擎读，strix 不读）。如果 strix 后端已弃用，这几句标注可以简化为一句总说明。
3. **通知内容描述可再准确**：界面写"包含漏洞标题与目标地址"，实际 `NoticePayload` 还含
   summary、severity 与各级计数。目前是**描述不全**，不是错误，优先级低。
4. **「扫描结束时通知」的语义值得重新想一遍（第 4 处的根因，产品决定）。**
   `should_notify` 现在把"完成通知"和"阈值过滤"串在一条链上（`dispatch.py:308` → `:311`），
   于是"这次跑完了"这个**与发现无关**的事实，被"发现了多严重的问题"这个**与完成无关**的
   阈值卡住。文案已经改成如实说明，但更干净的模型是**分开**：完成回执按开关发、
   发现告警按阈值发。这样默认配置下用户也能收到"跑完了"，而不必把阈值降到
   `info` —— 那会让每一条低危都变成一次打扰。属于行为变更，未擅自改。
