# ADR-001：凭据用不透明令牌，不用 JWT

- **状态**：已采纳（后端任务 1）
- **相关**：契约 §0.3、§1.2、§3.1；任务说明里的「JWT（access token + refresh token）」

## 背景

后端任务 1 的原文要求：

> 认证：实现登录接口，用 JWT（access token + refresh token），
> 密码用 bcrypt/argon2 哈希存储。

而契约 §1.2 明确写了相反的话：

> 会话值应是**不透明随机串**，服务端存哈希。不要用 JWT —— 本地单机部署
> 不需要无状态扩展，而 JWT **无法即时吊销**（改密码后旧令牌仍有效）。

两份文档冲突。契约的权威性是事先约定的（「契约是唯一事实来源」），
但任务 1 自己留了退路：「多用户/角色权限先不做（**除非契约里已经要求**）」——
说明它承认契约可能已经覆盖了这些议题。

所以问题不是"听谁的"，而是**哪一条在技术上是对的**。

## 决策

**按契约实现：不透明随机令牌，服务端存 SHA-256 摘要。**

同时保留任务要求的 access + refresh **语义**，只是不用 JWT 这个形式。

## 理由

### 1. 契约给的理由是技术事实，不是偏好

「JWT 无法即时吊销」——这是 JWT 的定义决定的。要做到"改密码后旧令牌立即失效"，
必须维护一张吊销表（`jti` 黑名单）并在每个请求上查它。

**那就已经不是无状态了。** 此时付出去的是 JWT 的全部成本：

- 签名密钥的生成、轮换与泄露处置；
- 时钟偏移与 `exp` / `nbf` 的边界处理；
- 算法混淆攻击面（`alg: none`、HS256↔RS256 混用）；
- 声明（claims）的 schema 演进；

而收回来的"无状态扩展"在这个部署形态里**用不上** ——
契约的部署形态是本地/单机 Compose，一个进程，没有多副本共享会话的需求。

### 2. 本平台的威胁模型把"吊销"抬成了硬要求

契约 §0.3 论证加登录时的核心一句：

> 这个平台的危害不是"读到数据"，是**替攻击者发包**。
> 受害者（目标方）看到的来源是**用户的 IP**。

凭据泄漏在这里的后果是「有人用你的身份对任意目标发起攻击扫描」。
所以"改密码能立刻踢掉所有旧会话"不是体验优化，是**事故响应能力** ——
泄漏发生后唯一的止血手段。

用 JWT 而做不好这一步，等于在最需要止血的地方留了个窗口。

### 3. access + refresh 的语义可以用别的方式给到

任务要求那两个 token，要解决的其实是这个用户问题：
**既不能让会话永久有效，也不能让用户干到一半被踢出去。**

不用两段式也能满足：

| 手段 | 实现 |
| --- | --- |
| 短期有效性 | 会话绝对过期 12 小时（`Max-Age=43200`） |
| 活跃用户不被踢 | **滚动续期**：每次使用时把 `expires_at` 往后推 |
| 写放大控制 | 续期节流到 60 秒一次（否则每个请求一次 UPDATE） |
| 即时吊销 | `revoked_at` 软吊销；改密码时批量吊销全部会话 |

而且这样做**少了一整类边界情况**：「refresh 过期了但 access 还没」、
「并发刷新导致 refresh 轮换竞态」、「access 有效期内用户被停用」——
这些在 JWT 双令牌方案里都要单独处理，而它们是真实存在的失败模式。

### 4. 机器通道的令牌本来就不是 JWT

契约 §1.2 把两条通道分开，而机器通道（`Authorization: Bearer svx_…`）
**从一开始就是**哈希入库、可即时吊销、可限定 scope 的设计。
给它套 JWT 只会让它失去 scope 之外的可吊销性。

## 代价（如实记）

1. **每次请求多一次数据库查询**（按 `token_hash` 查唯一索引）。
   在"单机、几个浏览器标签、几十次扫描"的规模下，这是一次微秒级索引查找。
   如果将来要横向扩展到多副本 + 高 QPS，这会变成瓶颈 ——
   到那时该做的是换 Redis 会话存储，而不是改回 JWT（JWT + 吊销表一样要查）。
2. **不能跨服务免验证地传递身份**。如果将来拆出第二个服务要验这份凭据，
   它得能读到同一张表或调一次校验接口。
   在"本地单机"这个前提下，这是一个假设，不是当下的成本。
3. **需要自己做令牌生成与摘要**（十几行）。
   代价是必须做对：用 `secrets.token_urlsafe(32)`（256 位熵）、
   SHA-256 摘要入库、按摘要查而不是按明文查。

## 保留了换回去的可能

令牌格式被封装在两处：`app/core/security.py` 的
`new_session_token` / `new_machine_token` / `token_digest`，
以及 `app/auth/service.py` 的 `resolve_session` / `resolve_token`。

将来真要换 JWT，改的是这五个函数，**业务代码一行不动**
（`app/auth/deps.py` 之后拿到的仍然是一个 `Identity`）。

换的时候请先回来改契约 —— 因为换的代价不只是这几行代码，
而是重新失去上面第 2 条讲的那种止血能力。

## 影响

- 契约不变。
- 任务说明的「JWT」未按字面执行，**语义已覆盖**。
- 新增测试：
  - `test_session_token_is_opaque_not_a_jwt`（形状断言，
    挡住"以后有人顺手换成 JWT"）
  - `test_change_password_revokes_existing_sessions`（吊销能力）
  - `test_revoked_token_stops_working`（机器令牌即时吊销）
