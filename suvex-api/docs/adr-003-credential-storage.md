# ADR-003：provider 的 API key 加密存储

- **状态**：已采纳（后端任务 2）
- **相关**：契约 §2.9、§3.2、§1.3；任务 2 的要求 2 与验收标准

## 背景

任务 2 的要求：

> `api_key` 绝不能明文存库：用对称加密（比如 Fernet，密钥来自单独的环境变量，
> 不要和 JWT 密钥复用）加密后存储，返回给前端时只回显掩码（如 `sk-****abcd`），
> 不回显完整明文。

验收标准：

> 密钥全链路不出现明文落盘或明文日志（检查一下日志中间件有没有把请求体整个
> 打出来，那样会把明文 api_key 打进日志，这是常见的安全事故点，务必检查）

## 决策

### 1. 加密：Fernet，密钥来自独立的 `SUPEX_SECRET_KEY`

`api_key` 与口令、会话令牌都不一样 —— **它必须能被还原**（服务端要拿它去调 LLM），
所以哈希这条路从一开始就不通，只能是可逆加密。

选 `cryptography` 的 Fernet（AES-128-CBC + HMAC-SHA256，
"encrypt-then-MAC"）而不是自己拼 AES：自拼的加密代码里，
IV 复用、MAC 校验顺序、填充预言这几类错误**不会在正常使用中暴露**，
只在被攻击时暴露。而这类代码的测试通常也测不出来。

> **关于"不要和 JWT 密钥复用"**：本项目没有 JWT 密钥
> （见 [ADR-001](adr-001-auth-credentials.md)，契约否掉了 JWT，
> 用的是不透明令牌，根本不产生签名密钥）。这条约束在这里的等价物是：
> **这条密钥只做加密**，不签名、不派生会话、不校验任何东西。
> 一条明文密钥只承担一个职责，泄漏时影响面才是可界定的。

### 2. 掩码单独存一列，而不是每次解密算出来

`api_key_hint` 存的是可直接展示的掩码。这个取舍值得写清：

| 方案                     | 读接口（`GET /providers`）         |
| ------------------------ | ---------------------------------- |
| 每次解密算掩码           | 明文进内存、越过 service 层，**每个列表请求都如此** |
| 预先存好掩码（**采用**） | 读路径上**永远不出现明文**          |

代价是掩码与密文必须同时更新 —— 所以它们只在
`providers/service.py` 的 `_apply_key()` 一个函数里被写入，别处不允许碰。

收益是一句**可验证**的话：「明文只在真的要调用 LLM 的那一刻才被解开」。
这是能写成测试的（`test_unreadable_ciphertext_is_reported_clearly` 里
改了密钥之后读接口照样正常，恰好证明它没碰过密文）。

### 3. ★ 掩码放进独立字段 `apiKeyMask`，**不放进 `apiKey`**

这是本任务里最关键的一处设计，而且它的理由是**具体的、有代码依据的**，
不是"更清晰"这种泛泛之谈。

前端 `ProviderPanel` 保存时这样拼 payload：

```ts
apiKey: keyEdited ? draft.apiKey : account.apiKey
```

也就是**没动 key 时把 `account.apiKey` 原样带回服务端**。这是"密钥不回填"
能成立的前提（输入框是空的，保存时必须带上原值，否则改个显示名就把凭据清空）。

**如果服务端在 `apiKey` 里返回掩码**，那么用户只改一个显示名、点保存：

1. 前端把 `sk-****abcd` 放进 payload；
2. 服务端把它当成新 key，加密存下来；
3. 真凭据被覆盖，**静默地**；
4. 界面显示"已保存"。

没有任何报错，也没有任何日志。用户要等到下一次扫描认证失败时才会发现 ——
而那时他大概率会去怀疑模型名或网络。

把掩码放进独立字段之后，`apiKey` 永远是空串，
上面那条 payload 拼装**自然就是对的**。这是
"让连接本身不产生危险"，而不是"加一层校验挡住危险"。

服务端仍然加了一道兜底（`crypto.looks_like_mask`：值等于掩码 → 视为不改凭据），
但那是第二道防线 —— 它不是设计依据，而是给"读出来、改一个字段、整体提交"
这类我们控制不了的客户端留的余地。

### 4. 日志：先审计，再加兜底

审计结论写在 `app/core/logging.py` 的模块 docstring 里：
**本后端没有请求体日志中间件**。唯一的请求日志是 uvicorn 的 access log，
它只记 `方法 路径 HTTP状态`；FastAPI / Starlette 自身也不打印请求体。

但"现在没有"不等于"以后不会有"，所以做了两件事：

1. **把审计结论写成测试**：`test_plaintext_key_never_reaches_the_logging_module`
   在 `Logger._log` 这一点上拦截**所有**被送进 logging 的消息
   （不是用 `caplog` —— 那是 handler 层，而脱敏过滤器会就地改写
   `record.msg`，于是 caplog 看到的已经是掩码，断言永远通过）。
   验收脚本里还有一条对应的端到端检查：打**真实运行中的 uvicorn 进程**
   的日志（含访问日志），确认明文 key 不在里面。
2. **加一层正则脱敏兜底**（Formatter + Filter 双份，因为 Formatter 能覆盖
   traceback，而 Filter 能覆盖 uvicorn 自己的 handler）。
   它挡的是"手滑"，不是"设计错误"——
   正则只能识别长得像密钥的东西。

### 5. 密钥丢了会怎样：明确报错，不假装没事

`SUPEX_SECRET_KEY` 丢失或更换 ⇒ 已存凭据全部解不开。这时：

* **读接口照常工作**（它不需要明文），`hasKey: true`、掩码正常显示；
* `POST /providers/{id}/verify` 返回 **200 + `status: "failed"`**，
  `error` 说明"无法解密，最可能是密钥被更换或丢失"
  （失败本来就是这个接口的正常业务结果，见契约 §3.2）；
* 绝不显示成"未配置" —— 那会让用户以为是自己没填，然后重填一遍
  （而重填**确实能修好**，所以更糟：真正的原因被掩盖了）。

`GET /providers` 里也**不**把这种 provider 标记成异常：读路径不解密，
它无从知道。要发现这件事，必须有一步真的去用它（verify 或扫描）。

## 代价（如实记）

1. **运维上多一条必须备份的密钥。** 丢了它，所有 provider 凭据都没了，
   只能重新填。这句话写进了 README、`.env.example` 和启动警告。
2. **明文在内存里存活的那段时间无法主动擦除。** Python 的 `str` 不可变、
   也没法手动清零，而 HTTP 客户端最终也要把它变成 `str` 放进请求头。
   能做到的是**缩小窗口**（只在调用前解密、不缓存、不落日志），不是消除它。
3. **没有做密钥轮换。** 换密钥意味着要一次性重新加密所有行，
   那是一次需要停机或双密钥并存的迁移。当前没做，也不假装支持 ——
   真要轮换，得先加一个"用旧密钥解密、用新密钥加密"的迁移脚本。
4. **协议的判定不完美**（见下）。

## 相关的一处不完美：探测协议按接入点判定

`ProviderAccount.kind` 只有 `cloud` / `local`，而 Anthropic 与 OpenAI
都是 `cloud`。所以协议只能按 host 判定（含 `anthropic` → Messages API）。
自建网关转发 Anthropic 协议时会判错。

要真正做对，得给 `ProviderAccount` 加一个 `protocol` 字段 ——
那是前端类型变更，按契约的规矩记在 §7 的待改清单里，不在本任务做。

## 影响

* 契约升到 **v0.3**：新增 `apiKeyMask` 字段、凭据加密一节、
  三个错误码、以及"为什么掩码不能放进 `apiKey`"的完整论证。
* 新增迁移两个：`54eaafabd74c`（明文字段 → 密文 + 掩码）、
  `698537531e16`（移除 `scans.provider_id` 外键，见下）。
* 顺手修掉一处**历史漂移**：模型上有一条与主键完全重合的唯一约束，
  SQLAlchemy 建表时跳过了它，于是每次 autogenerate 都报一次假差异。
  现在 `alembic revision --autogenerate` 是干净的（零 Detected）。

> **为什么同一次任务里动了 `scans` 的外键**：`test_deleting_a_provider_used_only_by_finished_scans_works`
> 直接把 `IntegrityError` 摆了出来 —— 一条**已完成**的扫描也拦住了 provider 删除，
> 而契约 §6 的意图明显是"只拦未结束的"。`RESTRICT` 无法表达这个区分，
> 而它是历史引用不是完整性约束。详见 `app/scans/models.py` 的注释。
