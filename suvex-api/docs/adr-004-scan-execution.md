# ADR-004：扫描执行 —— 子进程编排，而不是进程内调用

- **状态**：已采纳（后端任务 3）
- **相关**：契约 §3.3、§3.3.1、§5；任务 3 的六条要求

## 背景

任务 3 要求「用子进程或 strix 的 Python SDK 在隔离环境里启动一次扫描，
扫描要跑在独立进程/容器里，**不能阻塞 API 主进程**」，并记录 strix 侧的
run 标识；还要有状态机、终止（不留僵尸）、重跑、并发上限。

## 决策

### 1. 子进程，不用 Python SDK

strix 确实是一个 Python 包（`strix-agent`），可以 `import`。
但**不用它的 SDK**，而是拉它的 CLI：

| | CLI 子进程（采用） | 进程内 import |
| --- | --- | --- |
| API 进程的依赖 | 完全隔离 | strix 的 litellm / openai / docker SDK 会进同一个进程 |
| 崩溃影响面 | 子进程崩了，API 不受影响 | 一次 OOM 或段错误带走整个 API |
| 终止 | 杀进程树，干净 | 只能靠线程/信号，而 strix 是多 agent 异步的 |
| 版本升级 | 换一个 venv 里的可执行文件 | 要重装整个 API 的依赖 |
| 代价 | 要自己管进程 | — |

决定性的两条是**依赖隔离**与**终止**。实测确认了这个担心不是假想的：
装 `strix-agent` 拉进来 80 多个包（litellm、openai-agents、docker、boto3、
reportlab、huggingface-hub……）。它们装进 API 的 venv，
一次 strix 升级就可能改掉 API 用的 pydantic / httpx 版本 ——
而那种问题会以"API 某个接口突然 500"的形式出现，方向完全不同。

所以本机把它装在**独立的 venv** 里：
`E:\Program Files (x86)\strix-venv\Scripts\strix.exe`，
配置项 `SUPEX_STRIX_COMMAND` 指过去。

### 2. 状态归我们，执行归 strix

我们不解析 strix 的内部状态，只看两样东西：

* **退出码**（它的公开契约：0 完成 / 1 致命 / 2 发现了漏洞）；
* **工作目录里的 `strix_runs/<run_name>/`** —— run 标识就从这里读。

**不去猜 `events.jsonl` 的内部格式。** 那需要在有 Docker 的机器上
观察一次真实运行才能确定字段；凭猜测写一个解析器，产出的会是
"看起来在工作、实际解析错字段"的代码 —— 而它不会报错。
契约里记了这件事，作为后续工作。

### 3. 凭据只走环境变量

`STRIX_LLM` / `LLM_API_KEY` / `LLM_API_BASE`。

* **不进 argv**：命令行参数在进程列表里对同机其他用户**可见**
  （`ps aux`、任务管理器）。验收里有一条断言专门钉这件事。
* **不写 `--config` 文件**：strix 支持 `--config /path/to/config.json`
  且那份文件里要放 `LLM_API_KEY` —— 那就成了磁盘上的第二份明文凭据，
  与任务 2 的「密钥全链路不出现明文落盘」直接冲突。

### 4. 并发上限：一层是安全阀，不是优化

默认 `SUPEX_MAX_CONCURRENT_SCANS=1`。一次扫描会拉起沙箱容器并
**对真实目标发包**，失控的并发意味着同时打多个目标、费用不可控，
而且界面上说不清"现在到底在跑几个"。

### 5. 终止：按**树**杀，而且不猜退出码

`terminate_tree()` 在 Windows 上用 `taskkill /PID <pid> /T /F`，
POSIX 上用进程组（`killpg`）。

两个都是实测逼出来的结论：

* 一开始 Windows 上写的是"先 `taskkill /T`（不带 /F）给它机会清理沙箱容器，
  超时再强杀"。**实测证明那是错的** —— 不带 `/F` 时直接子进程一退，
  `taskkill /T` 就报告成功，而**孙进程还活着**（测试用"孙进程持续写心跳文件"
  抓到了：终止之后心跳还在更新）。而"给它机会清理容器"这个理由本身也不成立：
  Docker 容器是 dockerd 的子进程，不是 strix 的子孙，`/T` 从来管不到它们。
* **不猜退出码**：终止时状态先落库、再杀进程，而且收尾逻辑只对 `running`
  的扫描生效。否则我们杀出来的退出码会被当成"它自己失败的" ——
  "用户终止的"变成"失败的"，而那是两件不同的事。

### 6. 孤儿回收：两种情况的处理**不同**，都不猜

服务重启之后，上一次留下的 `running` 行：

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| pid 还活着 | **终止它**，置 `aborted` | 我们丢了 Popen 句柄，拿不到退出码、也不知道它跑到哪了。一个**没人能终止的攻击进程**比一次白跑的扫描危险得多 —— 用户以为服务停了，其实还在替他打目标。 |
| pid 已经不在 | 置 `failed`，原因写"结果不可知" | 我们不知道它成功还是失败。报 `completed` 是编造。 |

> ⚠️ **如实记一条平台差异**：Windows 上 `Popen.terminate()` 是
> `TerminateProcess` —— 强杀，进程收不到任何可处理的通知。
> 于是 uvicorn 被强杀时 **lifespan 的关闭钩子不会执行**，
> `scheduler.stop()` 里"终止所有在跑的扫描"那段等于没跑。
> 也就是说**强杀 API 进程会留下无人跟踪的扫描进程**，
> 唯一的兜底是下次启动时的 `recover_orphans()`。
> 优雅停止（Ctrl+C、`docker stop`）不会有这个问题。

## 实现时被测试抓到的两个真 bug

1. **并发上限根本没生效。** 三个 `POST /scans` 各自在后台线程里捅调度器，
   三个线程**同时**算出"当前在跑 0 个"，于是各启动一个 ——
   日志里三个 pid 都在，而配置写的是 1。
   `FOR UPDATE SKIP LOCKED` 挡不住它：三个线程认领的是**三条不同的**扫描行，
   行锁彼此不冲突。真正要互斥的是"数名额 + 认领"这一整段。
   修法：整个 `tick()` 串行 + 名额按**数据库里 `running` 的行数**算
   （内存里那份在"认领了但还没启动完"的窗口里偏小），
   外加 `pg_advisory_xact_lock` 让多 worker 也安全。

2. **`recover_orphans()` 会杀掉自己刚启动的扫描。** 它把所有 `running`
   都当成"上一次运行的遗留"，于是对自己正在跟踪的进程下手。
   修法：先把 `self._procs` 里还活着的排除掉。

两个都是"只在特定时序下出现"的问题，靠读代码很难发现 ——
它们的共同点是**测试真的去跑进程、真的去数状态**，而不是断言函数被调用过。

## 测试与验收怎么做的

`SUPEX_SCAN_RUNNER=fake` 的替身后端**不是 mock**：它同样 spawn 一个真的子进程
（还带一个真的孙进程持续写心跳文件），只是那个进程不做任何真实攻击。
所以队列、进程监督、杀进程树、退出码解释全都是真的在跑。

> ⚠️ **测试与 CI 绝不能跑真实渗透测试** —— 它们会向真实目标发包。
> `tests/conftest.py` 在导入任何 app 模块**之前**就把后端设成了 `fake`。
> 那不是"让测试快一点"，那是避免违法行为。

真 strix 的链路由验收脚本单独验（`verify_real_strix`）：在进程内直接调
执行后端，断言命令拼装、凭据不在 argv、环境变量注入、退出码解释、
日志尾部可读 —— 并**真的把 strix 跑起来**。

## 代价（如实记）

1. **API 进程多了一层进程管理**：pid 跟踪、孤儿回收、杀树。
   这些都是必须写对的地方，而写错的后果（僵尸攻击进程）比一般 bug 严重。
2. **状态回写最多延迟一个轮询周期**（默认 2 秒）。所以 `POST /scans`
   之后会主动捅一下调度器，让状态立刻变 —— 否则用户会看到"排队中"卡两秒。
3. **没有做扫描总时长上限。** strix 自己有 `--max-turns` 与 `--max-budget`，
   我们用它们；但"这个扫描跑了 6 小时还没停"这种情况目前只能靠 `abort`。
4. **`strix_runs/<run>/events.jsonl` 没有解析。** 于是 Activity 页目前只显示
   我们自己发的生命周期事件（启动/完成/失败/终止），看不到 strix 内部
   agent 的真实动作。要做那个，必须先在有 Docker 的机器上跑一次真实扫描、
   把格式看清楚 —— 见契约里记的后续工作。
