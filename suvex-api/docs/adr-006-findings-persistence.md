# ADR-006：漏洞持久化与统计的唯一数据源

- **状态**：已采纳（后端任务 5）
- **相关**：契约 §2.2、§2.3、§3.4、§3.4.1、§3.4.2；任务 5 的四条要求

## 背景

任务 5 要求：漏洞落库为结构化记录、状态流转带操作人留痕与时间戳、
批量更新，以及**统计接口同时服务 Overview 与 Findings 两页、保证数字一致**。
验收标准把最后一条单独拎出来了：

> Overview 和 Findings 两个页面的统计数字来自同一个查询逻辑，不会对不上。

## 决策

### 1. ★ 统计只有一处实现，Overview 调它

`findings/service.py` 的 `stats()` 是**唯一**算统计的地方；
`overview_metrics()` **内部调它**，不自己写一遍 SQL。

不允许"各自的页面再数一遍"，理由不是洁癖：

> 两次独立的计数查询在并发编辑下会取到**不同的快照** ——
> 一次在改状态之前、一次在之后。于是两页显示 13 与 12，
> 而**用户不知道哪个对**。那种不信任会扩散到整个产品。

这条不只靠自觉：验收脚本里有一条端到端检查
（`★★★ 统计数字与逐条列表完全一致`），它把 `/findings/stats` 的输出
与 `/findings` 列表**逐条数出来的结果**做比较，并且**逐档用筛选接口交叉验证**。
统计逻辑一旦分叉成两处，这条会红。

### 2. 两个轴分列，来源也分开

契约 §2.2 强调 `verification` 与 `status` 绝不可合并。任务 5 落实时
明确了它们**各自的来源不同**：

| 轴 | 来源 | 谁改 |
| --- | --- | --- |
| `verification`（证据强度） | strix 的 `confidence`（`high`→`verified`、`medium`→`partial`、`low`→`none`） | agent 产出，**机器不改它** |
| `status`（处置状态） | 一律从 `new` 开始 | **人的判断**，机器不改它 |

第二条在实现时是个具体的约束：**重复导入绝不能动 `status`**。
外部工具后续补写 `vulnerabilities.json` 时，如果顺手把整条记录覆盖过去，
用户标过的"误报"会变回"待确认" —— 而在"每轮调度都导入"的频率下，
这个 bug 会表现成"我标的误报过两秒又变回去了"。

有一条测试专门钉这件事（`test_reimport_does_not_touch_human_decisions`）。

### 3. 反证不丢，折进 `reasoning`

strix 的记录里有 `assumptions`（成立假设）/ `counterevidence`（反证）/
`confidence_rationale`（置信度依据）—— 它们恰恰是**诚实标注证据强度**的
关键材料。契约的 `FindingDetail` 里没有它们的位置。

**丢掉是错的**：丢掉之后，一条"发现了但存在反证"的记录会和一条铁证如山
的记录在界面上长得一模一样 —— 而这正是任务 5 背后那个更早的偏好
（区分"已坐实"与"未完成"）要防的事。

处理方式：折进 `reasoning`，带明确的小标题（`【反证】`/`【成立假设】`/
`【置信度依据】`）。不改契约的字段表，信息也不丢。

### 4. 认不出的值落**保守**的那一档

两处都是刻意的：

* **严重度认不出 → `info`**，不是 `medium`。把严重度不明的发现显示成"中危"
  是在**放大**它。宁可低估也不要高估 —— 一份"全是中危"的报告会让人
  对整套分级失去信任。
* **CWE 认不出 → `misconfiguration`**（最中性的兜底），不是 `injection`。
  分类是用来**筛选**的：用户按"注入"筛选时混进来一堆无关条目，
  他会开始不信任这个筛选。

两处都会记日志，所以"认不出"这件事本身是可观测的。

### 5. 批量流转是**原子**的

批量里有任何一条非法 → **整批都不改**。改一半会让用户不知道哪些生效了，
而"部分成功"在界面上最难表达（重试会重复改掉那些已经改过的）。

### 6. 时间线序号用 `max(seq)+1`，不是 `count(*)+1`

`(finding_id, seq)` 上有唯一约束。用 count 的话，**删过条目之后**新序号
会与已有的撞上 —— 那会是一个"删了东西之后就再也写不进时间线"的 bug。
（这条是写测试时想到的，`test_timeline_seq_is_unique_after_deletes` 钉住了它。）

## ★ 一次真实的对账：任务 4 的一个错字段

任务 4 里，我按"名字最可能对得上"猜了 `create_vulnerability_report` 的
参数结构，其中 `args["severity"]` 是纯猜的，并在代码里明确标了
**"载荷启发式，需要一次真实扫描来核对"**。

这次读 `tools/reporting/tool.py` 的签名，结论是：

> **`create_vulnerability_report` 根本没有 `severity` 参数。**
> 它由 `cvss_breakdown` 经 CVSS3 算出来（`_calculate_cvss`：
> `cvss.severities()[0].lower()`，`none` 归一成 `info`）。

也就是说那个分支**从来没有命中过**，而当时的测试还断言了
`detail["severity"] == "high"` —— 它之所以通过，是因为测试数据是我自己
按那个错误假设造的。

**那条"待对账"的标注在这里兑现了价值**：它指明了该去核对哪里。
如果没有它，这个错字段会安静地留在代码里，直到某天有人发现
"活动流里的发现事件从来没有严重度"。

现在：`severity` 只在调用方真的传了 `cvss_breakdown` / 结果里带了
`severity` 时才出现；**权威来源是 `vulnerabilities.json`**（任务 5 的导入路径读它）。

## 代价与边界（如实记）

1. **PoC 语言是启发式的。** strix 只存一个 `poc_script_code` 字符串，
   **不存语言**。我们靠 shebang 与语法特征判断，认不出写 `text` ——
   不编一个 `python`，因为前端会据此做语法高亮，猜错会让代码变成一片红。
   真做法是让上游记下语言，那是 strix 的事。

2. **CWE → 契约 8 分类是有损映射。** CWE 有 900 多条，契约只有 8 个桶。
   映射表覆盖了最常见的约 50 条，其余落 `misconfiguration`。
   这是**必然的**损失，不是可以补全的遗漏。

3. **`cwe` 与 `cvss_score` 存了但不出现在响应里。** 契约 §2.2 的 `Finding`
   没有这两个字段，加字段是前端类型变更。留着是为了将来做"按 CWE 聚合"
   与按 CVSS 排序时有据可查 —— 而不是现在就用。

4. **⚠️ 导入格式仍未与真实产物对账。** 测试用的是按源码字段名造出来的
   `vulnerabilities.json`。它证明"解析逻辑与源码描述一致"，
   不能证明"真实 strix 写出来的就是这样"。装好 Docker 后第一件该做的事
   仍然是跑一次真实扫描、把 `vulnerabilities.json` 与实际导入结果对一遍。
