# ADR-007：报告导出 —— 保留浏览器打印，并修正一条被夸大过的理由

- **状态**：已采纳（后端任务 6）
- **相关**：契约 §2.7、§3.5、§3.5.1；任务 6 的要求 2

## 背景

任务 6 要求实现报告的生成、导出（PDF + Markdown）与历史管理，并明确说：

> 导出为 PDF 和 Markdown：后端生成文件（可以用现成的库如 WeasyPrint 生成 PDF，
> 或者前端已经能拿到结构化 JSON 时，**评估是否继续用前端渲染导出更简单**——
> **两种方案你评估后选一个，并在 `/docs/api-contract.md` 里补充说明选择理由**。

契约 §3.5.1 在任务 0 就已经裁决过「本轮保留浏览器打印」。所以任务 6 的
真正工作不是重新选一次，而是**补上那次决策缺的事实核查**。

## 核查一：服务端 PDF 在本机可行吗

**可行，实测过。** 这台机器上 Edge 与 Chrome 都在：

```
C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe
C:\Program Files\Google\Chrome\Application\chrome.exe
```

无头打印实测成功：`--headless=new --print-to-pdf` 退出码 0，生成 41196 字节。

> **所以"服务端 PDF 做不到"这个说法不成立，必须修正。**
> 契约 §3.5.1 里"依赖成本落在最不该加的地方"那条理由也站不住了 ——
> 本机已经有浏览器，不必再拉 400MB 镜像。
> 如实记：那条理由在写契约时是**从通用情况推的，没有实测**。

## 核查二：那为什么不选它

关键问题：**服务端要打印的那份 HTML 从哪来？**

| 做法 | 结果 |
| --- | --- |
| 后端维护一套 HTML 模板渲染 IR | ❌ **第二套版式**。页边距、分页点、中文字体回退、表格断行各自演化 —— 正是前端整套报告 IR 要消灭的分叉 |
| 后端把前端的 React 组件搬过去渲染 | ❌ 要引入 Node + 前端构建产物，把"单机 Compose"变成三件套；且组件依赖浏览器 API |
| 前端把**渲染好的 HTML** 发给后端打印 | ⚠️ 可行，但那样后端只是个打印驱动 —— 而前端本来就能直接调打印，多一跳没有收益 |

**服务端 PDF 唯一的真实优势是"无人值守生成"，而无人值守的前提是它能独立渲染；
独立渲染就意味着第二套版式。** 两者不可兼得 —— 这才是决策的真正依据，
而不是"做不到"或"依赖太重"。

所以：**保留浏览器打印**。`ReportArtifact` 的 `{ kind: 'file' }` 分支继续留给将来。

### 什么情况下该重新评估

出现真正的无人值守需求时（定时报表、CI 产出、邮件附带报告）。
但那时正确的做法**仍然不是**写一套 HTML 模板，而是：

> 把前端「IR → HTML」的那层抽出来，让它能在构建期产出静态 HTML；
> 后端只负责调无头 Chromium 打印**那一份 HTML**。

契约 §3.5.1 的硬约束（"必须打印前端渲染的那份 HTML"）本来就是这个意思。

## 实现上做了什么

### 1. IR **逐字复刻**前端

`app/reports/document.py` 的每个字段、每处措辞、每个排序都照着
`report-document.ts` / `report-build.ts` / `report-markdown.ts` 抄，
并在注释里标了出处。常量表（严重度标签与定义、分类标签、状态标签、
验证程度标签、技能标签）在后端**另有一份** —— 因为它们要写进导出的文件。

**两份必须一致**，所以新增了 `scripts/verify_report_parity.py`
（契约 §3.5.1 原本就要求"那个脚本应当改为对着 API 跑"）：

* 从**前端源码**里解析常量表，与后端的逐条比；
* 比 `riskVerdict` 的四条分支与 `coverageNote` 的五条措辞；
* 比 IR 的字段集合（后端少一个字段会让前端渲染崩）。

⚠️ 它证明的是"后端复刻的常量与措辞与前端的**源码**一致"，
**不**证明"两端对同一份数据产出的 IR 逐字节相同" —— 那需要把前端的
`verify:report` 改成打后端 API，而那要求前端先接上 API。如实记。

### 2. `preview` 与 `generate` 走**同一份 IR**

两者都调 `ir.build_document`，唯一差别是 `provisional`（以及由此决定的
`meta.code`）。有一条测试把预览与生成的文档**归一化后逐字段比对**，
两者必须完全相同 —— 那是"预览=导出"的机器化保证。

### 3. ★ 说清"冻结"到底冻结了什么

实现时踩到一处，值得记下来：我一开始以为"报告内容冻结"意味着
**整份文档**都冻结，于是写了一条测试断言"改动漏洞后报告一字不变"。

**它红了。** 差异是条目里的 `处置状态：已确认` 变空了。

查证前端 `rebuildReportDocument` 之后确认：**它是拿活的 `allFindings`
按冻结 id 取回的**，所以 `statusLabel` 本来就反映当前状态。
后端必须照做 —— 否则预览显示"已修复"、下载的文件里写着"待确认"，
**"预览=导出"当场就破了**。

所以真正冻结的只有三样：

| 冻结 | 不冻结 |
| --- | --- |
| `findingIds`（收录哪些条目） | 条目的 `statusLabel` |
| `position`（报告内顺序） | 证据/描述文本（本来就来自 agent 产出） |
| `excludedCount` | —— |

**这是测试抓出来的一个真实认知错误**，已写进契约 §2.7 与测试注释 ——
不写清楚的话，下一个人会当成 bug 去"修"，然后预览与导出就对不上了。

### 4. Markdown 里两个防"静默损坏"的细节

照抄前端，因为它们各自对应一个**不报错**的失败：

* **表格单元里的 `|` 必须转义**。目标名出现竖线完全可能
  （`api.example.com|prod`），错位的表格只会静默地少一列；
* **内容含三反引号时围栏换成四个**。证据里嵌着 JSON 代码块很常见，
  三反引号会让围栏提前闭合，**后面的内容全变成正文**。

### 5. `from` 这个键

`scope` 是 discriminated union，其中 range 的字段名是 `from` ——
**Python 关键字**。第一版用 `model_validator(mode="before")` 把它挪成 `from_`，
结果被 `extra="forbid"` 提前拦下（`未识别的字段 scope.from`），
**整个区间报告用不了**。

正确做法是给 `from_` 一个 `validation_alias="from"` + `serialization_alias="from"`，
让它成为**真正被知道的字段名**。测试抓到了（`test_range_scope_accepts_the_from_key`）。

## 代价（如实记）

1. **后端多了一份 900 行的 IR 复刻。** 它必须跟前端保持同步，
   而同步靠对账脚本 + 注释里的出处标注，不靠记性。
   漏同步的表现是"某个字段在下载的文件里丢了"。
2. **`/reports/{id}/document` 是新端点**（契约原本没写）。加它是因为
   前端的"查看历史报告预览"需要一份复现的 IR，而下载端点只给文件。
3. **PDF 仍然要人工点对话框。** 这是浏览器原生行为，不是缺陷 ——
   前端提示语已如实写成"下一步该做什么"，而不是谎称"PDF 已生成"。
4. **对账脚本只比源码常量，不比实跑结果**（见上）。

## 测试

新增 33 个用例（`tests/test_reports.py`）+ 17 项对账（`verify_report_parity.py`）。
最关键的四条：

* `test_preview_and_generate_share_the_same_ir` —— 归一化后逐字段相同
* `test_excluded_count_is_frozen` —— 复现时不重算（重算恒为 0，
  会让"收录 0 条"的报告谎称"未发现问题"）
* `test_frozen_membership_survives_later_changes` —— 成员与顺序不变
* `test_entry_status_reflects_current_state_like_the_frontend` —— 状态**要**变
