# ADR-009：应急响应场景包 —— 为什么它是"一层皮"而不是第二个系统

- **状态**：已采纳（v0.41 / v0.43 应急响应场景包）
- **相关**：ADR-004（扫描执行）、ADR-005（事件接入）、ADR-006（发现持久化）、ADR-007（报告导出）

## 这件事是怎么被发现的

终审答辩的评委给了四条批评，其中第四条是：

> 通篇都在讲渗透测试，没有体现通用的安全智能体能力，比如应急响应，安全运营等能力

而这一条不是"多写一页 PPT"能解决的 —— 赛题原文（发榜单位：杭州安恒）写的是
「能够适应**渗透测试、应急响应、漏洞挖掘、逆向分析**等各类网络安全实战场景」。
渗透只覆盖了四分之一，而我们的产品当时**连一个应急响应的页面都没有**。

真正的困难不在于"再加一个功能"，而在于：**加完之后它还叫不叫同一个产品**。
一个系统如果在渗透之外又长出第二套决策循环、第二套事件模型、第二套报告格式，
那它就不是"通用安全智能体"，而是"两个勉强共用一个登录页的工具"。

所以这条 ADR 记的不是"我们做了应急响应"，而是**它为什么能只花这么小的改动量**。

## 决定一：场景包，不是子系统

复用现有四样东西，一行核心代码不动：

| 复用什么 | 在哪 | 应急响应怎么用 |
| --- | --- | --- |
| ReAct 决策循环 | `ctf2/runner.py`（外部 strix CLI 驱动） | 同一个循环，换提示词与镜像 |
| 三类事件留痕 | `events/`（`app/events/`，751 行，零改动） | 思维/工具/状态三类事件原样落盘 |
| 可插拔工具 | 沙箱镜像里装什么命令 | 装日志与取证工具，不新增 agent 工具 |
| 报告导出 | `scans/writeup.py` + `ctf2/writeup.py` | 新增一份 `workorder.md`，不新建格式 |

接入点是**两个本来就正交的枚举**（`core/vocab.py`）：

- `TargetKind`（`:63`）= url / repo / path / service / artifact，决定**怎么测**；
- `ScanGoal`（`:113`）= findVulns / captureFlag / verifyFix，决定**怎样算成功**。

渗透是 `(url, findVulns)`，CTF 是 `(url, captureFlag)`，复测是 `(·, verifyFix)`。
应急响应是 `(artifact, findVulns)` —— **两个值都已在枚举里**，缺的是"谁来认
`artifact` 这个形态"。

这一点值得单独写下来：`TargetKind.ARTIFACT`（`vocab.py:110`）的语义是
**只有附件、没有目标地址**（后端把附件解压成目录，按 `path` 形态交给执行后端）。
日志包、告警导出、磁盘镜像天然就是这个形状 —— 也就是说**这个枚举从一开始
就不是为渗透设计的**，它是"输入形态"而不是"攻击面类型"。

## 决定二：判据用第四种成功标准，而不是给 `findVulns` 加分支

第一版考虑过"复用 `findVulns`，靠提示词决定输出什么"。否决了，理由是
`findVulns` 的成功判据是"找到漏洞"，而复盘的成功判据是**每条结论都带得出证据**
—— 两者对"什么算做完"的定义不同，靠提示词区分会在报告口径、提交闸、
`status` 流转三处同时产生分叉。

最终落成 `ScanGoal` 之外的第四个枚举 `IrVerdict`（`core/vocab.py`）：
`confirmed` / `ruled_out` / `needs_follow_up`，默认 `needs_follow_up`。

★ **默认值必须是 `needs_follow_up` 而不是 `confirmed`**：这三档里只有
`needs_follow_up` 是"我还不知道"。另外两档都是结论，而一个默认给出结论的
系统，会在证据还没到的时候先说话。

`ruled_out`（排除了）的门槛比 `confirmed` 更高，必须写清四件事：判据是什么、
测了什么、观察到什么、覆盖了哪些变体。这条来自 `prompts/ctf2_ir.md` §二。

## 决定三：工单只产出文本，**不存在执行路径**

处置建议落在 `ctf2/workorder.py`，它只做三件事：解析模型输出的 `workorders`
数组、渲染成 markdown、写一份文件。

「不执行」不是"第一版先不做"，是**结构约束**。理由：留一个
`executor: Callable | None = None` 的钩子，半年后某次"顺手接一下 EDR"就会传
一个真的进来，而那时没人会回头读那段解释。

这条约束由 AST 扫描守着（`tests/ctf2/test_ir_workorder.py::test_no_execution_path_in_module`
参数化 26 个禁止标识符：`subprocess`/`Popen`/`socket`/`paramiko`/`iptables`…）。
★ 为什么用 AST 而不是"跑一次看看"：跑一次只能证明**那条分支**不执行，而这里
要证明的是**不存在**执行路径 —— 一个今天走不到的分支，明天可能因为一次无关
改动被走到。docstring 与注释不参与扫描（它们会**提到** `subprocess` 来解释
为什么不用它，那不是调用）。

## 决定四：四个字段缺一就降级，而不是丢弃

工单四段：动作 / 依据 / 风险 / 权限。缺任何一段 → **保留工单，但把级别强制降为
`needs_follow_up`**。

丢弃一条缺 `risk` 的建议，等于让一条真实发现凭空消失 —— 而"想到了要封这个 IP、
只是没写风险"仍然值得人看一眼。但级别必须降：审批人看到的级别是**可信度标签**，
它得同时反映证据与完整性。

唯一丢弃的情况是连 `action` 都没有 —— 没有动作的工单是感想。

## 代价（如实记）

1. **镜像必须重建才有工具**。`docker/ctf2-sandbox-ir/Dockerfile` 加一个包，
   重建之前容器里就是没有 —— 而 `scripts/verify_sandbox_tools.py` 会报 ✅，
   因为它读的是 Dockerfile 名单。这个坑踩过一次（`patchelf`/`gdb` 在
   `2de97ce` 写进 Dockerfile 而镜像是 2026-10-12 构建的）。

2. **`profile_for_category` 必须精确匹配**（`ctf2/runner.py:448`）。`forensics`
   含子串 `re`，子串匹配会让所有取证题静默进逆向镜像且无人发现。反之
   `image_for_profile` 对未知取值退回 base 并**只打 warning** 不报错。

3. **没有"多源日志归一"这个独立模块**。时间归一靠提示词里的决策表
   （「时间戳有多个时区混着 → 统一到 UTC 再排序，把换算规则写进报告」），
   不是代码。这够用，但意味着**同一份日志在不同模型下可能归一得不一样** ——
   这是一个已知的、尚未被测量过的风险。

4. **`read_attachment` 一次只收一个文件名**。这条已经写进 `prompts/ctf2_ir.md`，
   因为真的踩过：agent 写 `read_attachment("*.log")` 拿到"文件不存在"，
   然后据此得出"日志没采"的错误结论。
