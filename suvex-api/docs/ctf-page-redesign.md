# CTF 页重做（比赛场景）

- 状态：草案（2026-11-08）
- 触发：用户原话「CTF 页面我觉得需要重新做一下，在比赛中不好用，我最常用的还是对话页」

## 1. 现状为什么在比赛里不好用

现在是一屏**卡片网格**，每张卡上同时有：标题、分类、分值、状态徽标、优先级按钮、开始/继续、取消、提交、释放环境、题解、工单……比赛时真正要做的三件事被埋住了：

1. **扫一遍"哪些题还没解、哪些快解出来了"** —— 卡片信息密度低，一屏只能看 6–9 道；30 道题要滚很久。
2. **对一道题持续跟进** —— 点进卡片的弹窗/抽屉，信息是静态快照，看不到过程；而真正的解题过程在活动流/对话里。
3. **批量操作** —— 按分值排序后一次开一批、看到并发进度、随时停掉某道。现在只能一道道点。

用户说"最常用的是对话页"，说明**过程与交互本来就在 chat 里**，CTF 页却想自己承载全部操作，两边都做不深。

## 2. 方向：CTF 页退成"看板"，操作搬进对话

| 页面 | 职责 |
|---|---|
| CTF 页 | **只回答"现在什么状态、我该先做哪道"**：一张紧凑表格 + 批量操作 + 并发进度 |
| 对话页 | **一道题一个会话**：从 CTF 页点进来，过程、工具调用、候选、提交都在会话里发生 |

## 3. CTF 页（看板）

一行一道题，列固定：

```
状态点 | 题目 | 分类 | 分值 | 尝试 | 耗时 | 最后错误/候选 | 主操作
```

- 状态：未开始 / 排队 / 解题中（带轮次与耗时）/ 待确认 / 已解出 / 失败
- 主操作随状态变：`开始` / `查看`（跳对话）/ `确认`（有候选时）
- 顶部：比赛模式开关（按分值/难度排序、并发数展示、全部开始/全部停止）
- 支持键盘：`j/k` 移动、`enter` 打开会话、`s` 开始

## 4. 对话页里的题目会话

- 从看板点进来时，会话顶部固定一条**题目条**：题名、状态、分值、候选 flag、提交按钮
- 解题过程、工具调用、失败与重试都在消息流里（已有实现）
- 提交结果直接作为一条系统消息回显（错误次数、剩余额度）

## 5. 数据与接口

现有接口基本够用，需要补三样：

1. `GET /kernel/challenges` 返回里加 `lastRunAt` / `attemptCount` / `lastError`（看板列要用）
2. `POST /kernel/challenges/batch` —— 批量开始/停止（现在是一个个 POST）
3. 对话会话与题目关联：`chat_sessions.challenge_id`（或复用 project 字段），用于"从看板打开这道题的会话"

## 6. 分步

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 看板表格替换卡片网格（只读） | 30 道题一屏可扫完，状态/分值与活动流一致 —— **已落地**（`ChallengeBoard`，表头吸顶、行高 32px，实测 1000px 视口 28 行） |
| 2 | 行内主操作 + 跳转对话 | 点"查看"进到这道题的会话，题目条固定在顶部 —— **已落地**（`POST /chat/sessions/for-challenge/{id}` 幂等；`ChallengeBar` 带候选与两步提交） |
| 3 | 批量开始/停止 + 并发进度 | 比赛模式下一次开始 16 道，进度条实时 —— **已落地**（`POST /kernel/challenges/batch`，逐条结果 + 部分成功；看板勾选与并发进度条常驻） |
| 4 | 键盘操作 | j/k/enter/s 可用 —— **已落地**（光标行描边 + 自动进视野；输入框/按钮焦点下让位） |

## 7. 不做

- 不在 CTF 页里嵌入完整解题过程（那是对话页的活）
- 不保留卡片网格作为备选视图（两套视图意味着两套状态展示，会漂移）
