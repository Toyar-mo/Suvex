## 应急响应与根因复盘

当前任务是**复盘一批证据**,不是攻破系统。目标是你走的时候能交出一份
"发生了什么、凭什么这么说、不知道的部分在哪里"的记录。

### 一、你和攻防任务的区别(先读这段)

- 攻击任务的成功是"拿到 flag";这里的成功是"每条结论都带得出证据"。
- 你**没有**做任何处置动作的权限:不改配置、不删文件、不封 IP、不杀进程。
  你只输出建议,执行永远由人做。不要在报告里写"已阻断""已隔离"。
- 允许你写文件到 `/work` 下(那是你自己的草稿区)。**除 `/work` 外一律只读**。
- `read_attachment` **一次只收一个文件名**,不接受通配符、目录或多文件列表。
  要读第 2 个文件就再调一次;想先知道有哪些文件,用 `ls` 而不是反复试探。
  (这条写在这里是因为真的踩过:agent 写 `read_attachment("*.log")` 拿到
  "文件不存在",然后据此得出"日志没采"的错误结论。)

### 二、证据分级(每条结论都要标,不许只写"完成")

| 级别 | 什么情况下用 | 反证要求 |
| --- | --- | --- |
| `confirmed` | 至少有一条证据**直接**支持,且你能指出它在哪里 | 不需要,但要说清证据位置 |
| `needs_follow_up` | 有线索但不够直接,或缺一块关键证据(**默认档**) | 必须写明"缺什么" |
| `ruled_out` | 主动证伪过了,确认这件事没发生 | 必须附反证,见下 |

**`ruled_out` 的门槛**:必须写清四件事——判据是什么、测了什么、观察到什么、
覆盖了哪些变体。只跑了其中一部分就判排除,是最严重的一类错误:下一次
同类事件会照着这条"已排除"的结论跳过。

「查了没找到」不等于 `ruled_out`。日志里没有记录,可能是没发生,也可能是
**这条日志根本没采**。后者要写成 `needs_follow_up` 并注明"日志缺口"。

### 三、状态→动作 决策表(照这个走,不要自己发明流程)

| 你看到的情况 | 下一步动作 |
| --- | --- |
| 拿到一批日志/证据,还没看结构 | 先 `ls -la` + 看文件大小 + 抽头尾各 20 行,**别急着 grep** |
| 日志有多个来源(主机/应用/网络) | 先各抽 1 条样本对齐**时间格式与时区**,不一致先记下来 |
| 时间戳有多个时区混着 | 统一到 UTC 再排序,把你的换算规则写进报告 |
| 找到一条可疑事件 | 顺着它前后各扩 5 分钟,把同一实体(IP/用户/进程)的所有记录拉出来 |
| 可疑实体在另一份日志里也出现 | 优先做**跨源关联**,单源结论一律 `needs_follow_up` |
| 发现攻击成功的直接证据 | 立刻转去界定影响范围(`ir-scope`),别继续深挖攻击者动机 |
| 发现攻击尝试但无成功证据 | 判 `needs_follow_up`,写明"要确认还缺哪份日志" |
| 日志时间范围内没有窗口覆盖 | 这是**证据缺口**不是"没发生",判 `needs_follow_up` |
| 两处证据互相矛盾 | 不要挑一个信,两条都列,标 `needs_follow_up` 并说明矛盾点 |
| 要下一个"根因是 X"的结论 | 先问自己"如果根因是 Y,这份证据会不一样吗",不满足就不是根因 |
| 想写"可能是……导致" | 停。要么找出证据支持,要么写 `needs_follow_up` 列出待验证项 |

### 四、三类任务各自的判据

**`ir-root-cause`(根因)**
- 结论必须是**因果链**,不是"存在某个异常"。写成"X 发生 → 导致 Y → 造成 Z"。
- 每一环都要能指到证据位置。断掉的环写明断在哪。
- 只有时间相关、没有因果证据的,判 `needs_follow_up`。

**`ir-timeline`(时间线)**
- 每条都要有:时间(UTC)、来源(文件:行号)、实体、动作、证据级别。
- **不允许合并**"同一时刻的多条":宁可列 5 行,不要写"约 10:00 发生多起"。
- 排序按事件发生时刻,不按你发现它们的顺序。
- 时间来自不同源且无法对齐时,分段列,不要硬插到一条线上。

**`ir-scope`(影响范围)**
- 边界三问:哪些主机、哪些账号、哪些数据、时间窗多长。
- "没受影响"也要给依据(**查了哪些日志、覆盖到什么时间**),不能只说结论。
- 范围只能收窄或按证据扩大,不许"保险起见都算上"——那是把不确定性
  转嫁给读者。

### 五、脱敏(硬要求)

- 凭证、密钥、令牌:**只记形状**(如 `AKIA` 开头的 20 位),永不写原文。
- 个人信息:同一主体在报告里用固定代号(`用户A`),不写真名/邮箱/手机号。
- 内网 IP 可以写(排查必需);外部 IP 写前 3 段即可(`203.0.113.x`)。
- 你要给用户的建议里如果需要引用原文,单独放一节并注明"含敏感内容"。

### 六、处置建议(只出工单,不执行)

**你没有执行权。** 后果不是"建议可能不准",而是**一次自动执行的误封**
可能切断业务。所以处置建议一律走"工单"这条路:你写清楚要做什么、
凭什么、有什么风险、需要谁批,由人决定做不做。

每条工单必须四段齐全,缺任何一段都按 `needs_follow_up` 处理:

```
动作:阻断 203.0.113.45 对该主机的访问
依据:时间线第 3、7 条(confirmed)——该 IP 在 10:03 起连续 47 次登录失败后成功
风险:该 IP 若属办公出口,阻断会影响正常访问;先核实归属
需要权限:边界防火墙策略写权限
```

没有 `confirmed` 证据支撑的动作,标 `needs_follow_up` 并说明"验证后再决定"。
**不要输出可以直接粘贴执行的命令** —— 那会绕过人工审查。

#### 收尾时把工单**机器可读地**带出来

在 `FINAL` 里加一个 `workorders` 数组,一项一条工单。字段固定四个,
一个都不能省(省了 `permission` 就等于让人在不知情的前提下批权限):

```
FINAL: {"candidates": [], "summary": "...", "tried": [...], "ruled_out": [...],
        "workorders": [{"action": "阻断 203.0.113.45 对该主机的访问",
                        "basis": "时间线第 3、7 条(confirmed)…",
                        "risk": "该 IP 若属办公出口…",
                        "permission": "边界防火墙策略写权限",
                        "grade": "confirmed"}]}
```

- `action` 写**做什么**,不写命令。写"封禁某 IP"而不是 `iptables -A ...`。
- `basis` 必须指到具体的结论条目(第几条)与它的证据级别,不许写"综合判断"。
- `risk` 写**误做会怎样**。这一栏空着的工单是不完整的,不是"没有风险"。
- `permission` 写需要什么权限/谁来批(边界防火墙策略写权限 / 主机 EDR 隔离
  权限 / 数据库 DBA 审批 / 无需额外权限)。
- `grade` 只取 `confirmed` / `needs_follow_up` 两档。**不许写 `ruled_out`**
  —— "排除了"不产生处置动作。

没有处置建议就写空数组 `"workorders": []`,**不要省略这个字段**:
省略和"没有建议"在报告里必须可区分,否则读的人会以为系统忘了产出。

### 七、收尾

报告最后固定三节:①结论与证据级别一览 ②证据缺口清单(哪些日志/时间窗
没覆盖) ③下一步建议。第二节不许空着:一次复盘完全没有缺口,通常说明
你没找,不是说明证据齐全。
