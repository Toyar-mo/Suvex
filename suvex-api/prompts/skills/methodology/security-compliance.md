## 动作前的合规核查

> 平台有技术边界（`guard_tool_url` 白名单、容器网络隔离、`--read-only`），
> 但技术边界**不是**合规边界：白名单放行的地址里，仍然有不该做的动作。
> 下面这份清单补的就是那一层。

### 一、四个问题，按顺序问

1. **范围**：这个目标在本次授权里吗？
   题目给的地址 / 部署者配的白名单之外的任何地址 —— **停**，不要试。
2. **动作**：它属于下面哪一类禁止项？命中任意一条就不做：
   - 拒绝服务、资源耗尽型压测
   - 超出必要的高并发 / 高速扫描
   - 批量下载或抓取目标数据、删除或篡改目标数据
   - 破坏性载荷、持久化后门、WebShell 植入、反弹 Shell、计划任务
   - 对第三方系统（DNS、CDN、云厂商 API）发起攻击性请求
3. **力度**：高危验证是不是已经是最小必要？
   验证一次命令执行就够了，不需要跑十次。**能只读验证的，不要用写验证。**
4. **影响**：做完之后目标会不会变得不可用？
   会的话，先标记「需人工确认」，不要自己决定。

### 二、输出格式

做完核查后，用这个形状把结论说出来（简短，不需要长篇）：

```
合规核查: 通过 / 不通过
- 范围: OK / 越界（原因）
- 动作: OK / 禁止项（哪一条）
- 力度: 最小必要 / 可再降（怎么降）
- 残留: 无 / 有（是什么，怎么清）
```

### 三、赛后核查（做完之后）

- 有没有留下还在跑的进程、会话、连接？(`ps`、`netstat`)
- 有没有往目标写了不该留的东西？（自己上传的文件、临时账号）
- 报告里写的每一条证据，是不是都**真的来自本轮工具输出**？

### 四、⚠️ 最容易被绕过的一条

「先跑一下看看」是这类越界最常见的入口 —— 因为那一步看起来无副作用。
但**扫描本身就是有副作用的动作**：它会出现在对方的日志里、会触发告警、
极端情况下会打挂脆弱的设备。

所以判据不是"这个动作危不危险"，而是"**我有没有被授权对这个地址做这件事**"。
前者靠感觉，后者有清单。
