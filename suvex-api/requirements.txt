# 运行时依赖。版本用「下限 + 主版本上界」而不是精确锁定 ——
# 这是脚手架，锁死小版本会让后面的任务在补丁升级上耗时间。
#
# ★ 可复现构建靠 `requirements.lock`（2026-10-11 补），不靠这个文件。
#
# 这个文件是**给人读的、给依赖解析器用的约束**：它说"我要 fastapi 0.115
# 以上、1.0 以下"。而 `requirements.lock` 是**解析结果**：35 个包的精确
# 版本 + sha256 哈希。`Dockerfile` 装的是锁文件。
#
# ## 什么时候要重新生成
#
# 改了这个文件之后（加包、改版本范围）就必须重新生成，否则
# `Dockerfile` 装的还是旧的那份 —— 而症状是"我在 requirements.txt 里
# 加了包，构建出来的镜像却没有它"，看起来像构建缓存出了问题。
#
# ## 怎么生成（**必须在 Linux 上**）
#
# ⚠️ 不要在 Windows 上生成：那边拿到的是 `win_amd64` 的 wheel，
#    哈希与文件名都与 Linux 不同，生成出来的锁文件在 Linux 上装不上，
#    而报错是"找不到满足条件的版本"，看起来像依赖写错了。
#
# ```bash
# docker run --rm -v "$PWD:/w" -w /w python:3.12-slim sh -c '
#   pip install --quiet pip-tools
#   pip-compile --generate-hashes --output-file=requirements.lock requirements.txt'
# ```
#
# 生成后**要验证它能装上**（锁文件装不上比没有锁文件更糟）：
#
# ```bash
# docker run --rm -v "$PWD:/w:ro" python:3.12-slim sh -c '
#   pip install --no-cache-dir --require-hashes -r /w/requirements.lock'
# ```
#
# 然后推一次 CI —— `backend` job 会按这个文件装依赖，装不上就红。

# 口令哈希。选 argon2id 而不是 bcrypt：
#   · bcrypt 有 72 字节静默截断（长口令短语会被悄悄截掉，而用户不知道）；
#   · bcrypt 需要额外处理 cost 与盐的编码；
#   · argon2id 是当前密码哈希的推荐算法，内存硬度能挡 GPU 爆破。
# 契约 §0.3 允许「bcrypt/argon2」两者，这里取后者。
argon2-cffi>=23.1,<26.0

# FastAPI 解析表单/多部分所需（登录端点用 JSON，但保留以支持将来的文件上传）
python-multipart>=0.0.12

# provider 的 API key 落库前用 Fernet（AES-128-CBC + HMAC-SHA256）加密。
# 选库而不是自己拼 AES：自拼的加密代码里，IV 复用、MAC 校验顺序、
# 填充预言这几类错误不会在正常使用中暴露，只在被攻击时暴露。
cryptography>=43.0,<51.0

# LLM 连通性探测（app/providers/llm.py 的 `import httpx`）。
#
# ★ 这是**运行时**依赖，不是测试依赖。
#
# 它原先只写在 requirements-dev.txt 里 —— 在开发机上永远不会暴露，

# （Docker 镜像、新机器、CI 的运行时阶段）都会在**启动时**直接
