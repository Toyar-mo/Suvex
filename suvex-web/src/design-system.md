## 0. 一句话差异点

**CyberStrikeAI 的 Web 界面是一个「终端附件」——侧栏列会话、中间是聊天、
文件树里看 diff；它的叙事单位是"一次渗透任务"。Suvex 的叙事单位是"agent 此刻在做什么"，
界面是一条持续流动的行为流，任务和报告都是这条流的产物。**

这句话是整份设计系统的锚。下面每一条决策都能回溯到它。

具体到可观察的差异：

|          | CyberStrikeAI web UI           | Suvex                                         |
| -------- | ------------------------------ | --------------------------------------------- |
| 首屏     | 会话列表 + 输入框，等你发指令  | 已经能看到 agent 在动（状态点、正在跑的步骤） |
| 主视觉   | 侧栏 + 面板 + 聊天区，三栏切分 | 单列纵向流，一路往下读，没有并列面板          |
| 信息单位 | 会话 / 任务 / 标签页           | 事件（一次工具调用、一次判断、一次证据落袋）  |
| 背景     | 纯色深底，面板靠边框分隔       | 有动效的「场」，页面本身在呼吸                |
| 主色     | 蓝 / 红（安全产品惯用）        | violet（理由见 §2）                           |
| 密度     | 高密度表格与面板               | 大量留白，一屏只讲一件事                      |

> **品牌**：这个产品叫 **Suvex**。本项目最初是为开源工具
> [strix](https://github.com/usestrix/strix) 做的 Web 前端，2026-02 独立为 Suvex。
> 读到 `strix` 时先分辨：指**上游工具**（第三方，如 `usestrix/strix`）还是
> 历史命名残留。改名清单见 README。

> 注：CyberStrikeAI 的界面形态依据其官方 Web 使用文档

## 1. 为什么不做成「安全运营后台」

企业级安全运营台（SIEM / SOAR / 扫描器控制台）的共同形态是：深色、高密度表格、
左侧导航树、顶部指标卡、大量红黄色块。它们服务的任务是**在已知问题池里做筛选和处置**。

Suvex 要回答的问题不一样：**这个 agent 现在在干什么，我该不该拦它。**

这个差别决定了形态：

- 没有导航树 —— 导航树预设了"有多个功能模块"，而这里只有一个正在跑的流。
- 没有指标卡 —— 指标卡把"上个月的漏洞总数"推到首屏，那是报表语言。
- 没有红黄铺底 —— 严重度色只落在**结论**上（一条 finding 的徽标），不落在背景、
  边框、标题上。红黄一多，页面上所有东西都在喊，反而没有东西被听见。
- 大量留白 —— 留白是给"接下来会发生什么"留的。信息密度高到挤满，会让人错过
  agent 状态的变化。

一句话：CyberStrikeAI 那种形态是**给人看结果**的，Suvex 是**给人看过程**的。

## 2. 配色

### 为什么是 violet（`#8B7CF6`）

候选是 emerald / violet / amber，选 violet，三条理由：

1. **避开行业的既有语义。** 在安全工具里，绿 = 安全/通过，红 = 危险/失败，
   琥珀 = 警告。这是几十年终端和扫描器建立的共识，挪用它做品牌色会持续
   误导——一个纯 violet 的按钮，用户不会本能地读成"危险"。
2. **它和"待判断"这个状态同构。** 安全分析里最难的不是确认漏洞，而是
   **还不知道这是什么**。绿和红都已经是结论了，violet 是结论之前的那一格。
   这正是 agent 行为流里出现最多的状态。
3. **在近黑底上，violet 的亮度可控。** 从 `#171430`（衬底）到 `#A99BFF`（高亮）
   是一条完整的明度阶梯，可以在不换色相的前提下表达 hover / 选中 / 禁用。
   emerald 和 amber 在深底上更难做低饱和衬底——暗下去就变成了"脏灰"。

### violet 的风险，以及自律条款

必须承认：**violet 是 AI 生成界面最显眼的特征之一。** 机械检测器
（Impeccable detector）的 `ai-color-palette` 规则就是专门盯这个的——
"紫/紫罗兰渐变 + 深色底的青色"被列为最可识别的 AI tell。

选它是因为 §2 的三条理由成立，不是因为好看。但既然知道这个风险，
就要用纪律把"有理由的 violet"和"AI 默认的 violet"分开：

- **不许用紫色渐变。** 任何 `from-purple to-*` 的渐变，无论文字还是背景，直接否决。
  主色是实色，只有一个色相。
- **不许给主色加光晕。** 零偏移的 `box-shadow: 0 0 20px violet` 是 AI 味的主要来源。
  需要强调就用字重、字号、或 1px 描边。
- **主色不许铺大面积。** 一屏里 violet 的总覆盖面积应低于 5%。
  它是"当前项"和"可点"的信号，不是背景。
- **不搭配 cyan。** 深色底 + violet + cyan 就是那个被识破的组合。需要第二色时
  用同一 violet 阶梯的不同明度，或用中性的 `ink` 系列。

检测器在本文档定稿时对本项目返回空——这四条要保持住。

### 为什么保留绿/红/琥珀

因为**漏洞严重度是行业既有语言**。用户看到"高危"时预期它是红的，这个预期
比视觉一致性重要。所以：

- violet 只表达**结构**：选中、链接、当前项、进度。
- signal 色只表达**结论**：确认、待确认、失败、提示。且只出现在徽标、状态点、
  行头小图标上——**不允许做背景填充或大色块**。

如果用 violet 来表达严重度，用户每读一条都要停下来翻译一次。

### 近黑而不是纯黑（`#08090C`）

纯 `#000` 在 OLED 上会有轻微的边缘光晕（黑色涂抹感），而且和面板的层级差变得
只能靠边框撑。`#08090C` 带一点点冷紫倾向，让 violet 主色落在同一色域里，
不会像贴上去的。

### 层级靠 1px 线，不靠阴影

深色界面里阴影几乎不可见（黑底上的黑），真正的层级来自 `line` 描边和
`surface` 的明度差（`#0A0B0F` → `#0E1015` → `#14171E` → `#1A1E26`）。
阴影只负责"离开平面"的存在感，一律带 y 偏移，**不做零偏移光晕**。

### 对比度（实测，WCAG 2.1）

| token           | 色值      | 对 surface | 对 overlay | 允许用途                             |
| --------------- | --------- | ---------- | ---------- | ------------------------------------ |
| `ink`           | `#E7E9EE` | 15.7:1     | 14.4:1     | 正文、标题                           |
| `ink-muted`     | `#A2A9B6` | 8.1:1      | 7.4:1      | 副标题、说明、表头                   |
| `ink-faint`     | `#8A909C` | **5.9:1**  | **5.2:1**  | 三级文字、占位符。**下限，别再调暗** |
| `ink-ghost`     | `#454B57` | 2.2:1      | 2.0:1      | 仅装饰。**禁止承载任何信息**         |
| `accent`        | `#8B7CF6` | 5.7:1      | 5.2:1      | 链接、强调文字                       |
| `accent-bright` | `#A99BFF` | 8.0:1      | 7.3:1      | hover 态文字                         |
| `signal-ok`     | `#4ADE9B` | 11.1:1     | 10.1:1     | 已确认                               |
| `signal-warn`   | `#E8B454` | 10.1:1     | 9.2:1      | 待确认                               |
| `signal-risk`   | `#F07A6A` | 7.0:1      | 6.4:1      | 高危                                 |
| `signal-info`   | `#6FA8F5` | 7.8:1      | 7.1:1      | 中性提示                             |

`ink-ghost` 和 `line-strong` 低于 3:1 是**有意的**——它们是画线用的，不是读字用的。
一旦有人拿 `ghost` 写正文，这张表就是拒绝的理由。

#### ★ `ink-faint` 为什么按 overlay 而不是 surface 定值

这一条是踩出来的。`ink-faint` 原本取 `#7A808C`：对 `surface` 是 4.8:1，达标。
但同一个 token 落到 `surface-overlay(#1A1E26)` 上就只剩 **4.21:1** —— 挂了。
实际踩到的地方是批量操作栏的「取消选择」（底是 `bg-surface-overlay`）。

> **规则：某一级文字的对比度，必须按它可能出现的\*最亮\*承载面来验，不能按默认面验。**
> 否则同一个 token 在不同容器里时达标、时不达标，而单页抽查永远发现不了。

现在 `ink-faint #8A909C` 对 canvas / surface / raised / overlay = 6.2 / 5.9 / 5.6 / 5.2:1，全达标。

#### ★ 不要用 `opacity` 表达"禁用 / 弱化"

`opacity` 是乘在**整棵子树**上的，它不认识层级。向导第 2 步原来给不可选的技能行加
`opacity-45`，结果主标签 `text-ink` 从 15.7:1 掉到 **3.93:1**、描述掉到 **2.13:1** ——
而那段描述的全部意义就是解释"为什么这个技能不可选"。第 3 步的 `opacity-60`
把「去配置」这个**真可点链接**压到 3.57:1。

正确做法是**逐层降文字色**（`ink` → `ink-muted` → `ink-faint`）+ 减淡边框 + `cursor-not-allowed`：
视觉上照样是灰的，但每一层都还在 AA 之上。

#### 审计口径：排除 `aria-hidden`

纯装饰元素（事件行里的 `·` 分隔符、图标字形）标了 `aria-hidden="true"`，
不计入对比度要求 —— axe 的 `color-contrast` 规则同样跳过它们。
自建扫描脚本必须用同一口径，否则报告里会长期挂着几十条"永远不打算修"的失败项，
真正的缺陷反而被淹掉。

#### 语法高亮用独立色板，不借 `signal`

`signal` 是为**状态语义**选的（绿=通过、琥珀=待确认），要求彼此*语义*可辨；
语法色是为**连续文本里快速分词**选的，要求彼此*视觉*可辨。目标相反，不能共用。

早先直接复用踩了坑：`string` 借 `signal-ok(#4ADE9B, L=.561)`、
`number` 借 `signal-warn(#E8B454, L=.504)`，亮度比只有 **1.10** ——
对红绿色盲（约 6% 男性）两者都往黄灰塌陷，基本糊成一片。

见 §2.5 的 `syntax` 色板。

## 2.5 语法高亮色板

代码块底色是 `surface-sunken #0A0B0F`（比 `canvas` 还深一档）。下表全部为实测值：

| token             | 色值      | 对底色 | 说明                          |
| ----------------- | --------- | ------ | ----------------------------- |
| `syntax-plain`    | `#E7E9EE` | 16.2:1 | 普通文本                      |
| `syntax-comment`  | `#7A808C` | 4.9:1  | 注释 / `meta`（注释也要能读） |
| `syntax-keyword`  | `#A99BFF` | 8.3:1  | 关键字（紫）                  |
| `syntax-string`   | `#4ADE9B` | 11.4:1 | 字符串（绿）                  |
| `syntax-number`   | `#C98B3A` | 6.8:1  | 数字（赭）                    |
| `syntax-function` | `#9CC9FF` | 11.4:1 | 函数名（亮蓝）                |
| `syntax-property` | `#6E9BD1` | 6.8:1  | 属性 / 字段（暗蓝）           |
| `syntax-variable` | `#C4A7F0` | 9.5:1  | 变量（浅紫）                  |
| `syntax-operator` | `#9AA1AE` | 7.6:1  | 运算符（中灰）                |

### 解这组值的两条约束

1. **每个色对底色 ≥ 4.9:1。** 注释、运算符不因为"次要"就允许低于正文可读下限。
2. **共现频繁且语义易混的对，才做亮度分离：**

   | 对                      | 改前 | 改后     |
   | ----------------------- | ---- | -------- |
   | `number` ↔ `string`     | 1.10 | **1.69** |
   | `function` ↔ `property` | 1.26 | **1.68** |
   | `string` ↔ `plain`      | 1.42 | 1.42     |

**9 个类别想在单色底上两两拉开亮度是不可能的** —— 那需要约 11 倍动态范围，
暗端会直接掉到 4.5:1 以下。所以只对上面这几对做亮度分离，其余交给色相。

### 一处刻意保留的边界

`syntax-function` 与 `syntax-string` 亮度相同（都是 L≈0.561，比值 1.00）。
决定**不修**，理由：

- 两者对底色都有 11.4:1，可读性无虞；
- 蓝 ↔ 绿是红绿色盲（deuteranopia / protanopia）**最稳固**的色相分野，
  唯独在极罕见的蓝黄色盲（tritanopia，约 0.01%）下才会撞；
- 想再拉开就得让 `syntax-property` 继续压暗，那会把它推下 4.5:1 下限 ——
  用一个真缺陷换一个假缺陷，不划算。

保留的近似对都落在"蓝—黄"轴上，这条轴正是红绿色盲唯一保留的通道。

## 3. 字体

**界面文案统一中文。** 这是全站规则，后续新增页面与组件同样适用。

### 中文化的边界

译句子，**不译标识符**。这条线画在哪里很关键，画错会让界面变得没法用：

| 译                           | 不译（保持原文）                          | 理由                     |
| ---------------------------- | ----------------------------------------- | ------------------------ |
| 导航名、按钮、说明、错误提示 | 路由路径 `/scans`                         | 是地址，不是文案         |
| 漏洞标题、活动描述           | 端点 `GET /api/v2/search?q=`              | 要拿去复现，译了就对不上 |
| 严重度显示名（高危/中危）    | 严重度代码 `high` / `critical`            | 代码要和日志、API 对得上 |
|                              | 工具名 `sqlmap`、组件版本 `nginx 1.24`    | 是专有名词               |
|                              | 品牌与模型名 `DeepSeek` / `deepseek-chat` | 译了不可检索             |
|                              | 主键 `scan_01J8X2`、`agent-03`            | 是 ID                    |

判断标准：**这个字符串会不会被复制到别处使用？** 会，就不译。

### 两套正文族，按职责分，不按风格分

| 用途               | 字体（自托管）                                      | 为什么                                                                                             |
| ------------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 所有 UI（含中文）  | **Geist Variable** → 回退 **Noto Sans SC Variable** | Geist 负责字母数字的几何感；汉字不在 Geist 里，自然落到 Noto Sans SC。两者都是可变字体，字重轴一致 |
| 日志 / 代码 / 数据 | **JetBrains Mono Variable** → 同样回退              | `0` 带点、`1` 带底座、`l/I/1` 可区分 —— 读 payload 时这三组不能混                                  |

**都走 `@fontsource-variable` 自托管，不用 CDN。** 理由不是洁癖：这是一个
本地跑的渗透测试工具，可能在没有外网的环境里使用，字体链不能依赖 Google Fonts。

Noto Sans SC 包体 4.4MB，但按 `unicode-range` 分成 101 个分片，浏览器只下载
页面实际命中那几片（中位数 47KB）。所以"中文字体太大"不是拒绝自托管的理由。

**不用 monospace 装"技术感"。** 等宽只出现在：日志、代码、payload、
时间戳、端口号、哈希、计数。其余一律 sans。

`font-variant-ligatures: none` 是必须的 —— JetBrains Mono 的连字会把
`!=` 渲染成一个符号、把 `->` 渲染成箭头，读 payload 时这是致命的。

### 中文排版与拉丁文的三个反向差异

这套 token 是**为中文调的**，和常见拉丁文约定相反：

1. **不用负字距。** 拉丁大字收紧字距（`-0.035em`）是光学补偿，因为字母间
   本来有留白；汉字是满宽方块，收紧会让笔画相互碰撞。原来的负值已全部去掉。
2. **行高更松。** 汉字没有 x-height 的下伸空间，行距不足时上下两行会糊成
   一片。拉丁 1.5 倍可读，中文要 1.7 倍以上（base 已从 24px 提到 25px）。
3. **最小两档要加重。** 12–13px 的汉字笔画密集且细，同样 400 字重在近黑底上
   比同尺寸拉丁文明显更"虚"。`index.css` 里把 ≤13px 的档位提到 **450**
   （可变字体支持非整百字重），用 `:where()` 保证权重为 0，
   任何 `font-medium` 都能正常覆盖。

### 字阶

`2xs 11` / `xs 12` / `sm 13` / `base 14` / `lg 16` / `xl 20` / `2xl 24` / `3xl 32` / `4xl 44`（px）

基准取 **14px 而不是 16px**：这是长时间盯屏的工具型界面，主内容是列表和日志，
14px 能在一屏里多放两行而不损失可读性。正文另设 `max-width` 控制在 65–75ch。

### 实测对比度

改完字重后从浏览器读实际计算样式复核（不是从截图估）：

| 位置                           | 对比度  | AA        |
| ------------------------------ | ------- | --------- |
| 活动流主句 13px                | 15.66:1 | ✓         |
| 侧栏导航项 / 页面说明 13px     | 8.43:1  | ✓         |
| 指标卡标签 / 图表级别名 12px   | 8.05:1  | ✓         |
| 指标卡脚注 / 活动流元信息 12px | 4.80:1  | ✓（下限） |

> 注意：**视觉模型从 JPEG 截图估出的对比度不可信。** 它曾把这些 4.8:1 的
> 文字估成"约 3.5:1"。要判断对比度，从浏览器读 `getComputedStyle` 再用
> WCAG 公式算。

## 4. 间距与圆角

间距用 4px 基准，但**只暴露五档语义别名**，逼着自己做选择：

| token    | 值   | 用途                         |
| -------- | ---- | ---------------------------- |
| `tight`  | 8px  | 组内（图标与文字、徽标内距） |
| `panel`  | 16px | 面板内距                     |
| `gutter` | 24px | 页面边距                     |
| `bay`    | 40px | 区块之间                     |
| `rail`   | 56px | 侧栏宽度                     |

**圆角偏小**（默认 6px，最大 12px）。大圆角是消费级 App 的语言，读起来"软"。
工具型界面要的是精确感。`pill` 只留给状态点，不给按钮用。

两条例外硬规则：**组内要挤紧，组间要拉开**；**标题上方的空间永远大于下方**。
这两条比具体数字重要。

### 筛选区的布局约定（任务 5 定）

**1. 标签一律在上，不在左。**

> 「严重度：●严重 ●高危 …」这种行内混排看着省一行，代价是三重的：
>
> - 标签宽度不同 → 各组控件的起点就不同（`严重度` 3 字 vs `状态` 2 字，差一个字宽）；
> - 标签占掉首行开头，换行后的控件回落到**组**的左缘而不是**上一行控件**的左缘，
>   实测三行胶囊的左边界会变成 `62 / 24 / 50` 的台阶；
> - 带标签的组和不带标签的控件（搜索、排序）混在一屏，两套对齐基准并存，
>   整块筛选区看起来是散的。
>
> 改成标签独占一行后，**全条只剩一个左对齐基准**。

代价是多占一行高度。值得——筛选区本来就是"扫一眼就懂"比"省一行"重要。

**2. `flex-wrap` 是贪心装箱且不回溯的，别指望它紧凑。**
它把最宽的字段（严重度胶囊组 342px）放满一行后，后面的字段各自都塞不进剩余空间，
于是每个字段独占一行 —— 390px 下筛选区被拉到约 340px 高，把列表挤出首屏。

**窄屏用 grid、宽屏才用 flex-wrap**：

| 宽度       | 布局      | 实测高度 |
| ---------- | --------- | -------- |
| 320px      | grid 2 列 | 272px    |
| 390px      | grid 3 列 | 208px    |
| 640px 以上 | flex-wrap | 56–116px |

网格由浏览器统一分配列宽、**不看顺序**，高度立刻减半，且字段天然共享同一条左基准。
列数分档按最小可用宽度定，不是拍脑袋：320px 用 3 列时每格仅 85px，
搜索框含 `pl-7` 图标位会直接溢出。

> ⚠️ 胶囊组（严重度、状态）必须 `col-span` 跨满整宽 ——
> 胶囊最小约 62px，一格放不下两个就会叠成多行。
> 列数分档与 `col-span` 必须同步改，否则会残留空列。

**3. 只有筛选字段排进这套栅格。**
主操作按钮（「新建扫描」）不进去 —— 它是动作不是筛选条件，
混进表单栅格会让"填条件"和"执行"看起来是同一类事。

> 因此扫描任务页的工具条（状态胶囊 + 搜索 + 排序 + 主操作）保持无标签单行，
> 和漏洞发现页**不一致是刻意的**：那页没有"多组筛选字段"，只有一条工具条，
> 本身自洽，强行套栅格反而更差。

## 5. 动效

原则：**动效服务于"信息正在流动"，不服务于"这里有个东西进来了"。**

- 全局只有一条入场曲线 `ease-enter` = `cubic-bezier(0.16, 1, 0.3, 1)`（指数减速），
  且必须**从"已可见"出发**（`opacity` 从 0、`translateY` 只走 6px）。大幅位移的
  入场动画在事件流里会变成噪音——流本来就在动，再叠一层入场会让眼睛跟不上。
- `240ms` 以上算慢。只有背景首帧淡入用 `420ms`。
- **不要给每个区块配相同的入场动画。** 那是最明显的"模板感"来源。

### 背景动效（`components/effects`）

首屏背景是三层叠的「场」，见 `AgentField.tsx` 的注释。选型理由：

- **Threads**（WebGL 线场）：缓慢流过的线 = 数据正在通过。它是页面里**唯一**
  的持续运动，负责"活着"这个感受。
- **压角径向渐变**：把中心留亮、四角压暗，给后面的内容层留出可以落上去的地方。

> 原第 3 层 **DotGrid**（Canvas 点阵，跟随光标）**已移除** —— 它是全仓唯一
> 依赖 `gsap` 的地方，而 `gsap` 用的是 GreenSock 自有许可（非 OSI 开源），
> 而这一层是纯装饰。理由与记录见 `DEPENDENCIES.md` §4.3、`effects/README.md`。

两个约束（踩过）：

1. **同一个视口里不要挂第二个 WebGL 背景。** Threads 是逐像素 Perlin 噪声，
   纯 GPU 成本；再叠一个（Aurora/Silk 之类）会在集显上掉帧。
2. **色值传 sRGB，不传线性。** `ogl` 不做色彩空间转换（`Renderer` 里没有
   `outputColorSpace`），着色器输出直接进 sRGB 后备缓冲。按 three.js 的习惯
   传线性值会让线场暗到看不见——这正是第一版的问题。

### 帧率实测（改背景前必读）

Threads 的片元着色器每像素跑 40 次 `Perlin2D`，成本 = 像素数 × 40。
上游把内部渲染上限设在 1920，在 1080p 屏幕上等于不生效。实测
（RTX 3070 Ti / 1600×900，同一会话内交错多轮取中位数，避免整机负载把结论带偏）：

| 内部渲染上限         | 帧率             |
| -------------------- | ---------------- |
| 1920（上游默认）     | **19 fps**       |
| 1000                 | 46 fps           |
| **700（当前值）**    | **≈ 与基线持平** |
| 不挂 Threads（基线） | 108–180 fps      |

线条是柔和噪声，降到 700 看不出来。**要调这个值，先按上表的方法量，别凭感觉改。**

> 当时的记录：叠加 DotGrid（仅画点、只在光标附近改色）几乎不花钱，三层同时
> 挂载在三个视口（1600×900 / 1280×800@2x / 390×844@2x）实测 180 fps、零控制台报错。
> **该层后来已移除**（许可证原因，见 §5 与 `DEPENDENCIES.md` §4.3），上面这组
> 实测数字保留为历史依据 —— 它证明了"背景层数不是当时的瓶颈"。

### 强度：线场是氛围，不是主角

线场整层 `opacity: 0.55`，且用 `bottom-0 h-[78%]` 沉到画面下方。

理由是视觉评审给出的判断：满强度的紫罗兰波浪 + 点阵，读起来是
「AI 产品落地页的通用模板」，而不是「一个正在跑的工具」。而且线场默认走在
画布正中，正好压在标题那一行上——下沉之后它成了托住内容的「地平线」，
标题落在上方干净的区域里。

这条可以推广成一条通则：**背景动效的强度上限，是"它不再被单独注意到"。**
一旦有人第一眼先看到背景，就是过头了。

### 减少动效

`prefers-reduced-motion` 下**整层不挂载**，而不是挂载后隐藏。CSS 关掉动画
不会停掉 `requestAnimationFrame`，该烧的电一点没少。

## 5.1 动效规范（任务 8 定稿）

上面 §5 定的是**原则**；这一节是**可执行的值与判定**。
新写任何动效之前，先在这里找到它属于哪一档 —— 找不到，就是不该做的。

### 三条元规则

1. **动效服务于信息，不服务于装饰。**
   问一句"去掉它，用户会漏掉什么信息？"答案是"没有"——那它就该去掉。
2. **能不做就不做。** 一屏里的动效数量是有预算的。§9 说"等大卡片阵列"
   是偷懒，多而杂的动效同理：每一处都在动，等于没有东西被强调。
3. **动效不能挡住功能。** 这条是硬约束，下面有一整节讲怎么落地。

### 时长：四档，各有唯一职责

| token     | 值    | 唯一用途                 | 为什么是它                                          |
| --------- | ----- | ------------------------ | --------------------------------------------------- |
| `instant` | 80ms  | 按压反馈（`:active`）    | 必须比"感知到点击"更快。慢一档就变成"卡了一下"      |
| `fast`    | 120ms | 颜色 / 透明度 / 图标旋转 | hover、focus、chevron —— 高频、低信息量，要快要无感 |
| `base`    | 200ms | 状态切换、尺寸、数据条   | 需要"看得出来在变"，但不能让人等                    |
| `slow`    | 420ms | **仅**背景层首帧淡入     | 全站唯一允许用它的地方。用在交互元素上就是拖沓      |

另外三个**固定时长**的例外，不参与上面的分档（它们由内容决定）：

| 动效           | 时长  | 理由                                       |
| -------------- | ----- | ------------------------------------------ |
| `stream-in`    | 240ms | 高频事件流专用。见 §8                      |
| `word-settle`  | 500ms | Hero 标题逐词落定，错位 60ms，整段约 700ms |
| `flash-accent` | 900ms | 一次性高亮，衰减到透明                     |

**判定口诀：状态切换用 `base`，"来了个东西"用 `enter`。**
两者混用是"时长不统一"的主要来源。

### 曲线：三条，按语义分工

| token        | 曲线                             | 用于                                     |
| ------------ | -------------------------------- | ---------------------------------------- |
| `ease-enter` | `cubic-bezier(0.16, 1, 0.3, 1)`  | 入场：从"已可见的初态"收敛到终态         |
| `ease-exit`  | `cubic-bezier(0.4, 0, 1, 1)`     | 出场、收起。与 `enter` 成对              |
| `ease-state` | `cubic-bezier(0.32, 0, 0.24, 1)` | **状态切换**：选中、开关、展开、尺寸变化 |

> **为什么状态切换要单独一条对称曲线**：`ease-enter` 是强减速，
> 用在"展开 ⇄ 收起"上会让两个方向手感不同 —— 展开很顺、收起发钝。
> 侧栏折叠原先就是这个毛病（用 `enter` 跑 `width`），已改 `state`。
> 状态变化没有方向，所以曲线必须对称。

### 属性：默认用 `transition-ui`

`transition-ui` = `color, background-color, border-color, opacity, box-shadow, transform`。

它替掉了项目里原先的两种写法：

- `transition-colors` —— 加不了 `transform`，于是按压反馈没法做；
- `transition-all` —— **顺手把 `width`/`height`/`margin` 也带上了**，
  这是掉帧的常见来源，而且会让"文案变化"这类无关改动也变成动画
  （`LaunchButton` 就踩过：按钮文案在「启动扫描」/「正在启动…」间切换，
  宽度变化也被动画化）。

**布局动画（`transition-[width]` 等）全站只有两处**，且都经过判断：
侧栏折叠、严重度图表的数据条。两处都只改单个元素的尺寸、不触发兄弟 reflow。

### 微反馈：三条规则

关键操作必须有即时反馈。这里定义三个原子（在 `index.css` 的 `@layer utilities`）：

| 原子        | 效果                       | 用在哪                              |
| ----------- | -------------------------- | ----------------------------------- |
| `press`     | `scale(0.97)` @ `instant`  | 一般按钮、胶囊、状态切换控件        |
| `press-lg`  | `scale(0.985)` @ `instant` | 大控件（h-11 主 CTA）。缩放比例更小 |
| `settle-in` | scale 0.86 → 1，160ms      | "落定"：状态徽标变化、提交成功的勾  |

三条规则：

1. **按下必须立刻有反馈**，所以是 `instant`（80ms）。
2. **位移/缩放极小（2–3%）。** 作用是确认"收到了"，不是表演。
   密集列表里的大缩放会让点击显得很吵。
3. **禁用态不响应**（`:not(:disabled)`）。有反应但点不动，
   比完全没反应更让人困惑 —— 与 §12 的 `LaunchButton` 同一条。

**按压是全局唯一的"物理"反馈。** 不再有 hover 上浮 ——
`LaunchButton` 原先是 `hover:-translate-y-px`，方向和语义正好相反：
上浮传达"轻快、可随意点"，而这是全站风险最高的操作（真的会对目标发包），
它需要的反馈是"按下去有分量"。已改为按压下沉。

### 状态切换的反馈要"只因变化而播"

`StatusBadge` 在状态流转时重新落定一次（`animate-settle-in`），
用来回答"我点的那下生效了吗"——满屏徽标里一个 10px 字的替换太容易漏看。

但**首次挂载不播**：一进列表页 13 行徽标同时缩放落定一遍，
正是 §5 禁止的"给每个区块配相同的入场动画"。
实现见 `hooks/useChangeSignal.ts`（返回"变过没有"+"第几次变"，
`revision` 进 `key` 触发重挂载，`changed` 决定要不要挂动画类）。

### 提交成功的反馈：两个时长错开

外层横幅 `rise-in`（200ms，"它因为你的操作才出现"）+
内层勾 `settle-in`（160ms 缩放落定）——
读起来是"横幅来了，然后盖章"。

内层那个勾是有实际作用的：**绿色横幅和黄色警告横幅在余光里形状相同**，
用户得读完文字才知道成功了。落定的勾不用读。

> 顺带修掉的一处语义错配：`ScansPage` 的创建成功横幅原先用 `stream-in`。
> 而 `stream-in` 的定义是"高频刷新的流里新到的那一条" ——
> 用它等于告诉用户"这是后台流进来的一条"，而实际上是他自己刚点出来的。
> **动效方向应当对应因果，不只是"看起来动了一下"。**

### ★ 动效不能挡住功能（本项目的血泪条款）

这一条比上面所有数值都重要。项目里出现过四次同类事故，
都是"动效做得很好看，但它挡住了内容"：

| 事故                                  | 现象                                                       | 处理                                      |
| ------------------------------------- | ---------------------------------------------------------- | ----------------------------------------- |
| `AnimatedContent` 用在路由切换        | 渲染带 `invisible`，靠 gsap 放行；gsap 不跑 = **整页白屏** | 换成纯 CSS `animate-page-in`              |
| 同上，用在向导步骤                    | 同一失败模式；这次挡住的是**要填的表单和启动按钮**         | 换成纯 CSS，见 `NewScanWizard`            |
| `ScrollToTop` 用 `behavior: 'smooth'` | 无头/后台标签页**静默 no-op**，点导航后停在中段            | 改 `'auto'`（瞬时）                       |
| `gsap.from` 做标题入场                | 动画不推进 → 标题**冻在半透明**，且兜底也冻住              | 改纯 CSS，**只动 transform 不动 opacity** |

四条归纳出的通则：

> **1. 不要"先隐藏、等 JS 放行"。**
> 初态必须是可见的，动画只做叠加。GSAP 的 `from()` 语义正好相反，
> 用在大块内容或关键文字上就会得到一个静默的白屏/隐形缺陷。
>
> **2. 兜底手段不能和被兜底的东西共用同一个调度器，也不能只清理它的产物。**
> 实测记录（后台标签页，rAF 全程不触发）：
> · 用 `gsap.set(clearProps)` 兜 gsap → **无效**（清理也排在 ticker 上）；
> · 改成纯 DOM `removeAttribute('style')` → 当时有效，
> 但活着的 tween 会在 ticker 恢复时**把值写回来**；
> · 再加 `tween.kill()` → **依然失败**。
> 只要"显示"依赖某个调度器推进，就有永远不显示的路径。**要根治只能换掉设计。**
>
> **3. 功能性动作不能依赖动画能否播出来。**
> 把内容带进视野、展示页面内容、显示表单 —— 这些是功能，不是装饰。
> 动画可能因为任何原因不播（无头浏览器、后台标签页、省电模式）。
>
> **4. 安全性的来源是"默认可见 + 只动 transform"，不是"改用 CSS"。**
>
> 这里有一条我原本写错、后经实测更正的结论，留着以免重犯：
>
> **错的说法**："CSS 动画由文档时间轴驱动，不依赖 rAF，所以天然比 JS 可靠。"
> **实测**（Chrome，隐藏标签页）：`document.timeline.currentTime` **恒为 0**，
> CSS 动画同样停在 from 态（`playState` 还显示 `running`）。它并不免疫。
>
> 对照实验（同一个被冻结的动画，唯一差别是动什么属性）：
>
> | 动画只动    | 计算 opacity | 是否可见   |
> | ----------- | ------------ | ---------- |
> | `opacity`   | `0`          | **不可见** |
> | `transform` | `1`          | 可见       |
>
> 所以真正要去掉的不是"JS"，而是**"不可见的初态" + "依赖调度器放行"
> 这两件事的组合**。避开它之后，用 CSS 还是 JS 都安全。
> （`transform` 那条同时是"首屏文字类动效不许动 opacity"的第二个理由，
> 第一个是不推后 LCP —— 两个好处来自同一条纪律。）

### 首屏动效不能拖慢 FCP（验收项）

Hero 的动效设计围绕这条展开，三点：

1. **标题动效只动 `transform`，不动 `opacity`。**
   浏览器计算 LCP 时**会跳过 `opacity: 0` 的元素** ——
   一个"从透明淡入"的大标题会把 LCP 推后整整一段动画时长
   （见 [DebugBear：opacity 动画会拖慢 LCP](https://www.debugbear.com/blog/opacity-animation-poor-lcp)、
   [Shopify：不要用淡入动画遮挡 LCP 元素](https://shopify.dev/docs/storefronts/themes/best-practices/performance/dont-hide-lcp-image-behind-animations)）。
   实测：文字四词 opacity 恒为 1，处在 from 态时**只差一个 6px 位移**。
   > 这条纪律有**两个**好处，来自同一条规则：
   > ① 不推后 LCP；② 时间轴被挂起时内容仍然可见（见 D7/D8）。
2. **没有 JS 参与。** 词在 React 渲染时切好，每条只是 `animation-delay` 不同。
   没有动态 import、没有 SplitText、没有 ticker、没有兜底定时器 ——
   **没有需要兜底的东西**。
3. **昂贵的背景层推迟到首帧之后挂载**（`useAfterPaint`，双重 rAF + 兜底）。
   WebGL 初始化是几百毫秒级的同步开销，挤进首帧会拖长 LCP。
   背景是装饰，晚出现没有信息损失。
   > 注意区分：**装饰层可以用 `opacity` 淡入**（`fade-in`），
   > 内容层不行（用 `page-in`）。判据是"这层消失，用户会不会漏掉信息"。
   > 这条区分见 §5.1 的动效清单与 `tailwind.config.js` 里 `fade-in` 的注释。

实测（`vite preview`，本机）：主 chunk 在 **50ms** 加载完，
首帧文字已可见；Hero 背景的 chunk 到 **152ms** 才开始下载。
顺序是对的：先文字，后氛围。

> `useAfterPaint` 的兜底也是被实测逼出来的：`visibilityState === 'hidden'`
> 时 rAF **完全停发**（实测 1.5 秒内一次都没触发），
> 只写成功路径就会导致背景永远不挂载。所以补了一条 1 秒的 timeout。
> **"等条件成立"型门控必须回答：条件要是永远不成立会怎样。**

### 减少动效（`prefers-reduced-motion`）

三处配合，缺一不可：

1. **`index.css` 全局兜底** —— 把所有动画/过渡时长压到 `0.001ms`；
2. **`.press` / `.press-lg` 单独取消 `transform`** ——
   只压时长会让缩放变成"瞬间跳变"，对前庭敏感的用户仍是一次位移；
3. **JS 侧整层不挂载** —— `usePrefersReducedMotion` 让 WebGL/Canvas 背景
   直接不渲染。CSS 关动画停不掉 `requestAnimationFrame`，该烧的电一点没少。

### 新增动效的检查清单

写任何动效前逐条过：

- [ ] 去掉它，用户会漏掉信息吗？不会 → 不做。
- [ ] 时长落在四档里吗？落在哪一档、理由是什么？
- [ ] 曲线选对了吗？（状态切换用 `state`，入场用 `enter`）
- [ ] 用的是 `transition-ui` 吗？用了 `transition-all` 吗？（后者要说明理由）
- [ ] **它动的是 `opacity` 还是 `transform`？**
      内容必须用 `transform`（`page-in`）；只有纯装饰层才可以用 `opacity`（`fade-in`）。
      判据：**这层消失，用户会不会漏掉信息？**
      （实测：时间轴挂起时 `opacity` 版计算值为 0 = 不可见，`transform` 版为 1 = 可见。）
- [ ] **它的初态可见吗？** 任何"先隐藏、等某物放行"的写法都要否决。
      注意 CSS 动画的 `from { opacity: 0 }` 也算 —— **CSS 并不免疫挂起**。
- [ ] 它有没有可能挡住内容/延迟内容出现？
- [ ] 如果它依赖 JS/调度器推进，**不推进会怎样**？
- [ ] **带 `fill: both` 的动画动的是 `transform` 吗？**
      那会在结束后留下恒等矩阵 → 成为 `fixed` 后代的包含块（旧版 gsap 的坑）。
      没有 `delay` 就不要用 `both`。
- [ ] `prefers-reduced-motion` 下它怎么表现？
- [ ] 新加的 `animate-*` 类名在 `tailwind.config.js` 里有对应 token 吗？
      （实测踩过：写了 `animate-word-in` 但 token 叫 `word-settle`，
      结果动画静默不生效 —— 类名不存在时 Tailwind **不报错**，只是什么都不做。）
- [ ] **改完之后：我为什么认为它安全？这个理由经过隔离变量的实测吗？**
      （本节 D7/D9 两条都是"推理正确、一测就错"。结论要由对照实验支撑，
      不能由"改完看起来好了"支撑。）

## 6. 布局与响应式

### 断点与导航形态

三档，各有明确的形态，**没有一档是把功能藏进汉堡菜单**：

| 宽度     | 侧栏                        | 移动底栏                  | 可达入口                    |
| -------- | --------------------------- | ------------------------- | --------------------------- |
| ≥1024    | 展开 208px（可折叠到 56px） | 无                        | 6 个直连                    |
| 768–1023 | 图标轨道 56px               | 无                        | 6 个直连（图标 + 悬停提示） |
| <768     | 无                          | 底部 tab（4 常驻 + More） | 4 个直连，2 个一步进 More   |

平板给图标轨道而不是底部 tab，是刻意的：平板竖屏横向有富余、垂直空间宝贵，
而且轨道能让 6 个入口全部一步直连，底栏只能放 4 个。这直接满足验收里
「移动端操作路径不比桌面端多一步以上」——实测桌面 1 步、移动 2 步到 Settings。

### 折叠的默认值要看输入方式，不能只看宽度

图标轨道只显示图标，含义靠悬停提示补足。**触摸设备没有悬停，提示永远不出现**，
所以默认规则是：

- 有鼠标 + 宽度 <1024 → 折叠
- 触摸设备（`pointer: coarse`）→ 展开，无论多宽
- ≥1024 → 展开

只看宽度的话，触摸平板会折成一条只有图标的轨道，用户只能猜图标是什么。

### 滚动的归属

**让 document 滚动，不要给内容区加内部滚动容器。**

1. 移动端浏览器地址栏的收起依赖文档级滚动；内部滚动容器会让它永不收起，
   白白吃掉约 56px。
2. ReactBits 的 AnimatedContent 用 ScrollTrigger，默认 scroller 是 window。

所以侧栏和状态条用 `sticky`，不用 `fixed`；移动端底栏是 `fixed`（它本来就
不随内容走），主内容区因此必须预留 `3.5rem + safe-area` 的底部 padding。

### 状态条的窄屏策略：减字，不是横向滚动

第一版把状态条做成 `overflow-x-auto`，320px 下确实不溢出——但滚动条被我隐藏了，
信息还在 DOM 里、用户却不知道要往右划。**这比直接省略更糟。**

改成按断点渐进省略，每个断点下都恰好放得下：

- `<640` `● 3 running · DeepSeek · 184.3k`
- `≥640` 补 queued、token 百分比与预算
- `≥1024` 补 model 名与统计窗口

省略顺序是**先修饰词、再派生量、最后才动 provider**——provider 决定"能不能跑"，
比用量更重要。

### 占位页面不许编造

`pages/index.tsx` 里每个页面的 `planned` 都逐条对应 brief 给该入口规定的功能范围。
第一版我写了 "Delivered in task 2/4/5/6"，但 brief 只明确说过任务 3 是
Agent Activity，其余编号是我推的。**推断出来的具体值比留白更糟**：看的人
无法分辨哪个是排期、哪个是猜测。已全部删除。

## 7. 数据与组件约定

### 指标是算出来的，不是写死的

这条规矩在任务 7 **换了实现位置，但没有失效**：

- 任务 7 之前：`data/overview-mock.ts` 在前端从 findings/scans 集合现场派生
  （`activeScans` 来自 scans 的状态、`avgScanDurationSec` 来自已完成扫描的耗时…）。
- 任务 7 之后：整页读 `GET /overview` 一个端点，后端在**同一个事务**里算齐。
  派生逻辑没有消失，只是搬到了它唯一能保证一致的地方。

为什么必须搬：前端派生的前提是"手里有全量数据"，而 `GET /findings` / `GET /scans`
返回的都是**摘要**（契约 §3.4）。用摘要算出来的数字在某些边界上会与后端不一致，
而两个数字对不上时用户没法判断哪个是对的——那是最难被发现、也最伤信任的 bug。

代价写在这里：**Overview 页不再是实时联动的**。在 Findings 页改一条状态、
切回 Overview 会看到新数字（挂载时重新拉取），但停在 Overview 页不动时不会自己变。
需要真实时性的是活动流，那件事由 Agent Activity 页的 SSE 负责。

### 空值必须是 null，不能是 0

`avgScanDurationSec` 在无已完成扫描时返回 `null` 而不是 `0`。
0 秒和「没有数据」是两回事，把后者显示成前者会让用户以为扫描瞬间完成。
同理 `newHighSeverityDelta` 在无同比数据时是 `null`，界面显示
"No prior week to compare" 而不是 "+0"。

### 图表选型：水平条，不是环形

严重度分布用水平条形图：

1. 要读的是**每一级各有多少条**，不是占比。五个扇形比较长度人眼做不到，
   同一基线的条长可以直接比。
2. 严重度是有序的，水平条能自然按 critical→info 排列，环形图的顺序是任意的。
3. 标签可以水平写。而且**每条直接标数值**，不靠 tooltip——看板页不该要求悬停才给数字。

条宽按**最大值**归一，不按总和：按总和时最大的一级也只占 1/5 宽，整体会显得全是残条。

### 颜色是冗余编码，不是唯一载体

严重度同时用**颜色 + 文字标签**表达，相邻级别靠明度也能区分
（实测亮度比 1.62–2.38）。色觉障碍用户靠 "Critical/High/Medium" 文字读，
不靠颜色猜——这是图表里级别名不能省的原因。

`critical` 和 `high` 不用「同一色 + 不同透明度」区分：在暗底上那会把两者
压成接近的暗红。改用两个明确的实色（`#F07A6A` / `#C2544A`）。

### 一处实测出来的对比度修正

空状态的主 CTA 最初写成「深紫底 `accent-deep` + 浅字 `ink`」= **4.06:1**，
hover 时掉到 **2.74:1** —— 不达 AA。这是页面上唯一的行动按钮，不能将就。

改为「主色底 `accent` + 近黑字 `canvas`」= **5.98:1**，hover 提亮到
`accent-bright` = **8.36:1**。亮紫配深字是这套 token 里唯一能同时满足
「保持主色醒目」和「文字可读」的组合。

**按钮配色不要凭感觉挑。** 拿文字色和底色算一遍，两行代码的事。

### ink-ghost 不得承载信息

`ink-ghost` 是 2.17:1，§2 里写明它「禁止承载任何信息」。任务 2 中有三处误用了它，
已全部改掉：

- 活动流的事件类型标签 —— 它正是给色觉障碍用户的**文字替代通道**，必须可读
- 图表里的 0 值计数 —— 0 是「这一级确实没有」，是有意义的计数
- mock 数据声明 —— 「数据是假的」这句话不该藏在装饰色里
  （任务 7 把数据换成真的之后，这类声明只剩状态条上那句
  「用量统计未接入」，同样用 `ink-faint` 而非 `ghost`）

判断标准很简单：**这句话被删掉，用户会不会漏掉信息？** 会，就不能用 ghost。

### 开发工具不能出现在产品页面上

空状态的数据源切换按钮最初直接渲染，视觉评审判定为「开发痕迹」——它是对的。
现在用 `import.meta.env.DEV` 门控，生产构建里连同组件一起被剔除
（已用 `Select-String` 在 `dist/` 里确认过文案不存在）。

### 组件契约

| 组件               | 吃什么                                                  | 不认识什么     |
| ------------------ | ------------------------------------------------------- | -------------- |
| `StatCard`         | label / value（number→滚动，string→直显）/ icon / delta | 任何业务概念   |
| `ActivityFeedItem` | 一个 `ActivityEvent` + 跳转 href                        | 页面、路由形状 |
| `ActivityFeed`     | 事件数组 + isLive                                       | 数据来源       |
| `SeverityChart`    | `SeverityBreakdownEntry[]`                              | 数据来源       |

`value` 支持 string 是刻意的：`"14m"` 这种带单位的时长没有「滚动」语义，
硬套动画反而怪。所以 `formatDuration` 的结果直接传进去，不走 CountUp。

### CountUp 的可访问性

`CountUp` 每帧都在改 `textContent`，读屏器若跟随会念出几十个中间值。
所以动画数字标了 `aria-hidden`，**另给一份静态文本给读屏器**（`sr-only`）。
视觉用户看到滚动，读屏用户听到一个确定的数。改这个组件时别把 sr-only 拿掉。

## 8. 实时流的界面约定（任务 3 补充）

### 信息密度：一屏 5–9 条，靠折叠做到

Agent Activity 是要长时间盯着看的页面，密度靠**分层折叠**而不是缩小字号：

| 层  | 内容                                           | 可见性   |
| --- | ---------------------------------------------- | -------- |
| 1   | 类型标签 + 一行摘要                            | 折叠态   |
| 2   | agent / 时间 / 工具名 / 退出码 / 耗时 / 严重度 | 折叠态   |
| 3   | 完整命令、原始输出、PoC 源码、证据             | 按需展开 |

实测折叠态行高 **87px**，1600×900 下**一屏 9.3 条**，一屏字符量约 501。

为什么把「退出码、耗时、置信度」放第 2 层而不是展开里：**它们决定"要不要展开"**。
用户 90% 的时间只读 10% 的事件，第 2 层的全部意义就是帮他筛出那 10%。
反过来把一切平铺（原始日志的形态），一屏只能放 3 条，扫视效率归零。

### 颜色：8 种事件只给 3 种色

`EVENT_TYPE_TONE` 把八种类型映射到四档色调：告警/失败用 risk，
发现/生成 PoC/已验证用 accent 或 ok，工具调用/推理/完成**一律中性灰**。

理由：八种各给一个颜色，这一页会变成彩虹，而用户真正需要一眼看到的
「出事了」反而淹没在里面。日常动作不该抢注意力。

### 动效：只有新事件动，且只有 240ms / 4px

`stream-in` 从原来的 420ms/6px 收到 **240ms/4px**。位移再大或时长再长，
一屏里同时有几条在动就会晕。

已存在的事件在列表中位置变化时**完全不做动画**（不做 FLIP）。
实测：任意时刻只有 1 条带 `animate-stream-in`。

"哪些是新的"由 `useActivityStream` 在事件到达时给出（`latestBatchIds`），
而不是让组件自己 diff —— 组件 diff 需要记住上一批 id，会踩
「渲染期读 ref 不安全」和「effect 里 setState 级联渲染」两个坑。
首批历史回填不播动画：一进页面十几条一起淡入会很吵。

### 暂停的双向性

- 用户往上滚 → 自动暂停（阈值 48px，避免惯性滚动误触发）
- 用户滚回底部 → **自动恢复**，不用再点按钮

只做单向的话，用户看完历史还得手动点"继续"，很别扭。

**暂停期间事件照常收进缓冲**，只是不自动滚动。若暂停就停止接收，
用户回到最新时会发现中间空了一段，那比打断阅读更糟。
未读条数会显示在"回到最新"按钮和左侧名册对应 agent 上。

### 一个必须记住的布局陷阱

`AppShell` 有 `fillsViewport` 两种模式，区别只在最外层一个类：

| 模式             | 最外层                  | 用途                   |
| ---------------- | ----------------------- | ---------------------- |
| document（默认） | `min-h-dvh`             | 内容撑高容器，整页滚动 |
| viewport（本页） | `h-dvh overflow-hidden` | 锁死视口，内部自己滚动 |

**满视口页面若容器高度没被真正约束，内部滚动区的 `clientHeight` 会等于
`scrollHeight`，于是"不在底部"这个状态永远不出现** —— 自动跟随、暂停、
回到最新会全部静默失效，表面完全看不出问题。

这个 bug 实际发生过两次，都是靠 `clientHeight === scrollHeight` 这个特征抓到的：

1. `AppShell` 用了 `min-h-dvh`（它只是"至少一屏"，内容一多就跟着长）；
2. 改对之后仍然失效 —— 因为 `PageTransition` 包裹层（AnimatedContent）
   是 `display:block`，**打断了 flex 链**，包裹层被内容撑到 1439px。
   修法是给它加 `flex min-h-0 flex-1 flex-col` 透传高度。

### 窄屏的名册形态

桌面是竖直列表；**窄屏改成横向滚动的一行**。

原因：手机上高度是最稀缺的资源。竖直名册占 348px，实测把事件流挤到
**只剩 38px（320px 屏）**，等于不可用。横排后名册只有 62px，
事件流回到 359px / 635px。

配套的两处调整：窄屏隐藏"智能体"标题（不提供信息却占 40px）、
隐藏每块里的相对时间（横向块里最不重要的信息，留着会把"角色 · 状态"挤到截断）。

### 性能实测

在 `?rate=N`（**开发模式专用**，生产构建已剔除）下测出的数据：

| 事件速率           | 帧率      | 说明                      |
| ------------------ | --------- | ------------------------- |
| 1/秒（默认）       | 176 fps   | 实际使用场景              |
| 10/秒              | 151 fps   |                           |
| 33/秒              | 122 fps   |                           |
| 125/秒（`rate=8`） | 53–81 fps | 极端值，远超真实 SSE 速率 |

内存：约 70 条/秒 跑 50 秒（累积 1126 条），堆 125MB → 140MB，**无泄漏**。

两点诚实说明：

1. **`setInterval(8)` 实际间隔是 21ms**（实测），这是浏览器对嵌套定时器的
   钳制，不是我们的代码问题。所以 `rate=8` 的真实速率约 70 条/秒而非 125。
2. **5000 条上限的截断逻辑已实现但未跑到实测**：受上面的钳制，
   跑满 5000 条需要 70 秒以上，而更极端速率会被定时器压在同一水平。
   截断代码是 `merged.slice(merged.length - MAX_EVENTS)`，逻辑简单，
   但**要真正验证它，得让真实后端灌数据** —— 这是 mock 阶段无法覆盖的一项。

## 9. 组件规则

写新组件前先读这里。左边是「不要做」，右边是理由。

| 不要做                                   | 理由                                                    |
| ---------------------------------------- | ------------------------------------------------------- |
| 等大卡片阵列（图标 + 标题 + 文字 ×3/×6） | 卡片是偷懒的容器。等大 = 没有做取舍                     |
| 卡片套卡片                               | 层级用 `line` 和 `surface` 表达，嵌套卡片只会让边界糊掉 |
| 标题上方加 kicker / eyebrow 小标签       | 删除标签，让标题自己承重                                |
| 区块编号（01 / 02 / 03）                 | 除非顺序本身携带信息                                    |
| 渐变文字                                 | 强调靠字重和字号                                        |
| 玻璃拟态 / 装饰性模糊                    | 只在有具体功能（如遮罩后方内容）时用                    |
| 卡片上 >1px 的彩色左边框                 | 用徽标或色点表达状态，别用边框                          |
| 硬偏移阴影（`4px 4px 0`）                | 不是新粗野主义世界就别穿这身衣服                        |
| 零偏移彩色光晕                           | 那是装饰，不是深度                                      |
| 用 emoji / Unicode 符号当图标            | 图标要用同一套线条库或手工 SVG                          |
| 把等宽字体当"技术感"装饰                 | 见 §3                                                   |
| 用红黄铺背景或边框                       | 见 §2                                                   |

还有一条容易漏的：**浏览器自己画的那部分也要管**。
文字选区、插入光标、滚动条、焦点环、链接下划线偏移、表格数字的 `tabular-nums`
——这些默认值不属于任何设计系统，但用户每时每刻都在看。全部在 `src/index.css`
里按 palette 主题化过了，改配色时记得一起看。

### 跨页数据一致性（硬要求）

Overview 的严重度分布图与 Findings 列表**读同一个 store**，不接受"每页各建一套假数据"。

- 分布图**包含全部**漏洞 —— 与列表逐条对得上（13 = 13）；
- **只有"可操作"指标**排除 `false_positive`（本周新增高危及以上、已验证 PoC）；
- 排除这件事**必须写在屏幕上**（`falsePositiveCount` 提示），不能悄悄减掉。

任何"这张图少算了一些"的优化，都要先问：**用户能不能从界面上看出少了什么。**
看不出来就是错，不是简洁。

#### 任务 7 之后：这条规则多了一个"谁负责加载"的问题

两页读同一个 store 是**数据一致性**；而接上后端之后还有第二个问题：
**这个 store 是谁去拉的？**

原来的答案隐含在"数据是模块级常量"里 —— 无所谓谁拉。现在有所谓了，
而且踩到的症状是**说反话**：

| 现象 | 真相 | 为什么 |
| --- | --- | --- |
| 状态条写「未配置 · 去「设置」添加模型服务」 | provider 早就配好了 | provider 只在 Settings 页被加载过 |
| 侧栏写「0 运行中」 | 可能真有几个扫描在跑 | `/overview` 一个端点回全部指标，不经过 `scans-store` |

两句都比"不显示"更糟：前者会让人跑去重配一遍，后者让人以为系统闲置。

修法是给这两个 store 各加一个**幂等**的 `ensure*Loaded()`，
由 `Layout`（登录后的外壳，全局只挂载一次）调用。

> ⚠️ **不能放在 `TopStatusBar` 里。** 那个组件也被**公开的落地页**用，
> 而 `GET /providers` 在未登录时返 401 —— `lib/api.ts` 的 401 处理会
> 把访客**踢到登录页**，落地页就此不可访问。
> 「加载必须发生在登录之后」是一条硬约束，不是风格选择。

加载时机与数据一致性是同一件事的两面：**读者看到的那份必须是对的，
而"对的"要求它先被取回来。**

### 浮层的定位陷阱

`PageTransition` 的包裹层留下了一个恒等 `transform: matrix(1,0,0,1,0,0)`（视觉上完全看不出来）。
**恒等变换也会建立 containing block**，于是：

- `position: fixed` 在其中**相对包裹层**定位，不是相对视口 —— 底栏会跑到整页内容的最底端；
- 批量操作栏因此改用 `sticky`（顺带不用再按侧栏宽度算左偏移）；
- 详情抽屉改用 `createPortal(..., document.body)` 逃出这个层叠上下文。

遇到"fixed 定位莫名失效"，先查祖先有没有 transform —— 哪怕是恒等的。

### 按路由分包

四个真实页面走 `React.lazy`（`src/pages/index.tsx`），占位页保持同步引入。

**分包的理由是载荷分布不均，不是"文件大就要拆"**：漏洞详情页带着证据代码块、
PoC 与时间线（还有语法高亮的色板），报告页带着整份报告纸与印刷色板，
设置页带着四个表单面板；而用户第一次打开通常只落在总览。
不拆的话首屏要为几屏之外的内容付全部代价。

实测（`vite preview`，未压缩）：

|              | 拆前   | 拆后                                                      |
| ------------ | ------ | --------------------------------------------------------- |
| 主包         | 643 kB | 448 kB                                                    |
| 首屏实际加载 | 643 kB | **537 kB**                                                |
| 首屏未请求   | —      | ActivityPage 26 kB / FindingsPage 33 kB / ScansPage 33 kB |

rolldown 会自动把共享依赖提成独立 chunk（`findings-store` 同时被总览和漏洞发现依赖，
单独成块，不会重复下载）。切回已访问过的页面新增请求数为 **0**。

> ⚠️ **Suspense 的兜底块必须透传 AppShell 的高度链**（`flex min-h-0 flex-1 flex-col`），
> 和 `PageTransition` 完全一致。它不是普通 div —— 兜底会**替换**页面内容，
> 若掐断 flex 链，满视口页面（智能体活动）的内部滚动区会拿到
> `clientHeight === scrollHeight`，于是"不在底部"这个状态永远不出现：
> 自动跟随 / 暂停 / 回到最新 全部静默失效。
>
> 这个 bug 在本项目已因同样原因发生过两次，所以 `PageFallback` 的类名是刻意的。
> **验证方式**：冷启动直入 `/activity`，检查内部滚动容器的
> `scrollHeight > clientHeight`（实测 1849 vs 803，可滚动 1046px）。

`Suspense` 放在 `PageTransition` **内部**：`PageTransition` 用 `key={pathname}` 重挂载，
切路由时 Suspense 边界随之重置，兜底才会重新出现；放在外面这条就失效。

兜底 UI 做成**静止骨架**而不是转圈：本地 chunk 加载通常只有几十毫秒，
转圈会一闪而过，比不动更刺眼。

### 接真实后端时改哪里

**任务 7 已经改完了**：`src/data/activity-stream.ts` 的 `createSseEventSource`
就是真实实现，`activity-mock.ts` 连同它那份假事件源一并删除。

它返回与当初 mock 版**同一个** `EventSourceHandle` 接口，所以
`ActivityPage` 与所有组件一行没改 —— 接口先行的收益在这一次兑现了。

真实实现落地时处理掉的三件事（当时列在 mock 版注释里的清单）：

1. 断线重连与"补发漏掉的事件" —— `EventSource` 自带重连并发 `Last-Event-ID`，
   首次连接用 `?lastEventId=`；另外用 `GET /scans/{id}/events/recent` 做种子
2. 事件可能乱序到达 —— 消费端按 `at` 排序，不按到达顺序
3. 背压：突发大量事件时不能每条都触发一次渲染 —— 消费端按 120ms 批量合并

⚠️ 还有一个只有真接口才暴露的坑：**帧格式**。后端发的是命名事件
（`event: activity`），用 `es.onmessage` 收不到任何东西，必须
`es.addEventListener('activity', …)`。前端当时症状是"状态显示已连接但一条事件都没有"。

## 11. 报告：纸的介质（任务 6）

报告页是站内**唯一一个白底黑字**的地方。这不是风格选择，是介质选择：
前面十节描述的近黑底、signal 色、等宽字体，全部是为**屏幕上的操作界面**定的；
而报告要交付、要打印、要被钉在会议投屏上、要给非技术管理层读。
两者是"屏幕/纸"的区别，和深色模式/浅色模式是同一类问题 ——
所以报告另立一套色阶，**不是"两套配色不一致"的设计事故**。

### 印刷色阶必须另立，且必须实测

站内 signal 色直接印在白纸上有 4/5 不达标（中危 `#E8B454` 只有 **1.89:1**，基本等于没有颜色）。
语法高亮更极端：关键字 `#A99BFF` 在白纸上 **1.9:1**，字符串 `#4ADE9B` 更低。

| 用途     | 常量             | 底色      | 达标要求 |
| -------- | ---------------- | --------- | -------- |
| 严重度   | `PRINT_SEVERITY` | 白纸      | ≥ 4.5:1  |
| 正文灰阶 | `PRINT_INK`      | 白纸      | ≥ 4.5:1  |
| 语法高亮 | `PRINT_SYNTAX`   | `#F5F6F8` | ≥ 4.5:1  |

**这三组值都是搜出来、验出来的，不要凭手感改。** 两个实测教训：

1. 第一版 `PRINT_SYNTAX` 是我按直觉填的，并在注释里断言
   "number 与 string 在明度上分开"—— 实测明度比 **1.00**，两者根本没分；
   `property` 更是只有 **3.99:1**，不达标。
   用 `scripts/solve-print-syntax.mjs` 重解（在色相/饱和度固定下搜出落在
   目标对比度区间内的明度，再验算易混对）后：number↔string **1.44**、
   function↔property **1.42**、keyword↔variable **1.31**，全部 ≥ 4.5:1。

2. 纸面与屏幕有一个结构性差异：**站内是浅字深底，纸面是深字浅底**。
   白底上可用的对比度区间只有约 4.5~16:1，比暗底窄得多，
   所以"拉开明度"的余量很小 —— 只能靠"一个贴下限、一个压深"成对分离。
   number / property 因此刻意贴近 4.5 这条线，看着"不够艳"是对的。

### 预览与导出必须一致 —— 靠结构，不靠人工核对

验收要求"预览效果和导出内容一致"。实现方式**不是**写出两份渲染逻辑再逐字比对，
而是让它们根本没有分叉的机会：

```
                    buildReportDocument（唯一的内容真相）
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        ReportSheet     renderReport        （同一份 DOM
        （屏幕预览）      Markdown           交给浏览器打印）
              └───────────────┴───────────────┘
                   三者读同一份 ReportDocument
```

- **PDF** 走浏览器打印引擎，打印的就是屏幕上那个 DOM 本身 —— 版式一致是物理保证；
- **Markdown** 是 IR 的另一个消费者，只做"把字段排版成 Markdown"，不重新筛选/措辞/排序；
- 任何内容增减都必须改 IR，于是预览会同步变。

机器化验证：`npm run verify:report`（源码在 `scripts/report-parity.mts`，
用 Vite 的 `ssrLoadModule` 直接加载真实源码，不复制逻辑）。
12 组「范围 × 选项」组合、每条漏洞的全部字段逐条比对，
并反向检查"未勾选的 PoC / 判断依据没有泄露到导出里"。

⚠️ **任务 7 的两处变化**（读这一节时要知道）：

1. **输入数据换了来源。** 原来它 import `findings-mock` / `scans-mock`；
   那两个 mock 源已删除，现在读 `scripts/report-parity-fixtures.mts` 里
   一组**独立 fixture**。这是刻意的：检查验的是"渲染器覆盖完整"，
   不该随应用数据一起被删掉（那正是当时发生的事）。
   顺带修掉了一条**永远为真**的假检查（`!regex.test('') || true`）——
   它会在日志里给出绿色的 ✓，而真正的回归不会有人发现。
2. **生产链路不再用前端 IR 渲染。** 预览与下载都由服务端渲染
   （`POST /reports/preview` / `GET /reports/{id}/download`），
   理由是 `GET /findings` 只给摘要，前端**拿不到**构建报告所需的 detail ——
   早期症状很隐蔽：预览照常出来，只有「问题描述」和「证据」两节是空的。
   前端这两份实现（`report-document.ts` / `report-markdown.ts`）保留下来
   作为**对账参照物**（契约 §3.5.1 要求那个脚本"对着 API 跑"）。

### 编号只在生成后出现

报告编号 `RPT-YYYYMMDD-XXXX` 是**交付物的身份**，客户会拿它对账。
实测抓到的缺陷：预览显示 `RPT-...-3253`，下载得到的却是 `RPT-...-3310`。
两层原因，都已修：

1. 文档与历史记录各自取了一次 `new Date()` → 现在**先落库、再据落库记录构建文档**，
   编号在历史列表 / 预览 / 文件名 / 正文里是同一个冻结对象的四次引用；
2. 草稿由另一套 id 规则派生 → **草稿不显示编号**，如实写"生成后分配"。
   草稿本来就不是报告，编一个将来会变的编号只会误导。

### 报告里的"少"必须说出来

与 §7「任何少算都要让用户看得出来」是同一条原则，只是读者从用户变成了客户：

- **被选项排除的条数要冻结进报告**（`Report.excludedCount`）。
  复现历史报告时冻结快照里只剩被收录的 id，重算这个差恒为 0 ——
  一份"只含已确认"、恰好把 2 条待确认与误报全筛掉的报告，
  就会写着"本次范围内未发现问题"，**而真相是 2 条被筛掉了**。
  那不是没问题，那是没看。
- **中断的扫描要标注覆盖不完整**（附录 A 的"覆盖完整性"列 + 醒目提示），
  否则读者会以为整个目标都测过了。
- **"涉及目标"取覆盖了几个目标，而不是几个目标出了问题时**。
  没有收录条目时后者是 0，会写成"涉及目标 0 个"——读起来像"这次什么都没测"，与事实相反。
- 空报告是**可生成**的（"本次未发现问题"本身是有效结论），但必须与"筛错了"区分开。

### 打印样式（`src/index.css` 的 `@media print`）

打印时只保留"通往报告纸的那条链"：

```css
body *:not(:has(.report-sheet)):not(.report-sheet):not(.report-sheet *) {
  display: none !important;
}
```

这一条同时解决三件事：外壳（侧栏/状态条/页头/按钮）不进 PDF；
**祖先链保留**所以版式与屏幕一致；不需要给每个组件挂 `print-hide` 类，
也就不存在"新加了个面板但忘了加打印隐藏"这种必然发生的遗漏。
`report-entry` 类名供分页用（一条漏洞尽量整体落在同一页）。
`print-color-adjust: exact` 必须保留 —— 浏览器默认不打印背景色，
严重度色块的衬底会全部消失。**"克制"指不用大面积彩色，不是把必要信息也省掉。**

> 验证打印样式的方法（打印介质无法直接观测）：把 `@media print` 里的规则
> 抽出来作为普通 CSS 注入页面，再读 computed style ——
> 实测侧栏/页头被隐藏、正文与标题仍可见、纸张去边框去阴影、页面转白。

### 报告导出接口的边界（如实标注）

`lib/report-api.ts` 对两种格式都返回 artifact，但 **PDF 的 kind 是 `browser-print`**：
真实后端会用无头浏览器渲染出 PDF 文件流，本阶段没有后端，
因此调**浏览器打印引擎**（对话框里选"另存为 PDF"）。

这不是把问题藏起来，而是让接口形状与真实后端一致的同时，
把当前实现方式写进类型里：将来后端能出真 PDF 时只需返回 `{ kind: 'file' }`，
调用方按 kind 分发即可。**UI 上也如实说明**——浏览器无法告知用户是打印还是取消，
所以提示语给的是"下一步该做什么"，而不是谎称"PDF 已生成"。

> 副作用（已知，非缺陷）：`window.print()` 会阻塞渲染线程，
> 因此打印对话框未关闭前页面无响应。这是浏览器原生行为。

## 12. 设置：用户在这里交出凭据（任务 7）

设置页和站内其它页有一个本质差别：**用户会在这里粘贴 API key**。
这一节记的是由此产生的交互约束 —— 它们不是审美选择，是安全与信任要求。

### 密钥字段的六条约束

实现见 `components/settings/SecretField.tsx`。少一条都会在某个场景下泄露密钥：

| 约束                                             | 理由                                                          |
| ------------------------------------------------ | ------------------------------------------------------------- |
| 输入即遮蔽（`type="password"`）                  | 见下方「改过的一版」                                          |
| 显示要显式触发，且 20 秒后自动收回、失焦立即收回 | 不指望"用户会记得关掉"。这类页面常在共享屏幕/投屏时打开       |
| 遮蔽态不提供复制                                 | 遮蔽态复制 = 把明文送进剪贴板而用户并不自知                   |
| 复制后 2 秒清空剪贴板                            | 剪贴板是所有应用都能读的地方                                  |
| **已保存的密钥不回填**                           | 回填等于每次打开设置页都把明文搬进 DOM                        |
| `autoComplete="new-password"` + 关拼写检查       | `off` 在 Chrome 上常被忽略，浏览器会把登录密码填进 API key 框 |

> **改过的一版（教训）**：最初的做法是"输入时自动显示明文，方便用户确认"。
> 那是错的 —— 它正好把密钥暴露在**最容易被看到的时刻**：用户正在输入、
> 注意力在键盘上、旁边的人在看屏幕。所有主流控制台都是输入即遮蔽。
> 验收要求也写明"符合常见后台产品标准"，这条不该自作聪明。

> **"不回填"有个必须配套的动作**：输入框为空不代表没配，
> 所以保存时必须把原值带上（见 `ProviderPanel` 里 payload 的拼装）。
> 漏掉这一步，用户只想改个显示名就会把凭据清空 —— 这个 bug 很隐蔽。

### 保存反馈必须**常驻**，不能是 toast

验收明确要求"不要用一闪而过的 toast 糊弄"。落点是 `SaveBar` 的 `SaveState` 状态机：

| 状态        | 界面                                                   |
| ----------- | ------------------------------------------------------ |
| `idle`      | 不显示                                                 |
| `saving`    | 「正在写入…」，按钮禁用                                |
| `saved`     | 「**已保存 · 15:30:42**」—— 带**保存时刻**，常驻不消失 |
| `failed`    | 「保存失败：<原因>」，草稿保留、输入不丢               |
| `unchanged` | 「没有需要保存的改动」                                 |

三条设计理由：

1. toast 把"看过"当成了"知道"。用户抬头晚一秒就错过，而设置页要回答的
   "我这次改动存住了没有"在任何时刻都该有答案。
2. `saved` 必须带**时刻**：用户才能确认"这就是我刚才那次保存"。
3. `unchanged` 是独立一态：点了保存但没改过任何东西，**不能报"已保存"**——
   那是虚假的动作感。

> 保存是**显式动作**（表单持草稿，点保存才写 store），不做"改完即时保存"。
> 即时保存有三个说不清的地方：打字打到一半就是一次保存；用户看不到确认；
> 校验失败的中间态（半截 baseURL）也会被写进去。

### 分块保存，不是一个"保存全部"

provider / 沙箱 / 通知 / 账号是四件互不相关的事。一个全局保存按钮会让用户
改了一个开关却不敢点（怕连带提交别的），也让"哪一块没存上"无法回答。
每块自带保存条 —— 成功/失败都是自己的、可停留的状态。

### "验证"与"保存"必须是两个动作

`verifyProvider` / `sendTestNotification` 返回 `ActionResult`（**没有 nochange 态**），
而保存返回 `SaveResult`。两个类型分开是因为语义不同：

- 保存失败 = **没存进去**（网络/校验）
- 验证失败 = **存进去了但打不通**（key 无效、webhook 不可达）

混成一个动作，用户不知道该重填还是该重试。
`ActionResult` 用更窄的类型让"无改动"这个不可能的态在类型上不可表达。

### ★ 改了 key 必须作废"已验证"

实测抓到的缺陷：改 key 后 `verified` 沿用旧值 `true`，于是一个**从未验证过**的
新 key 显示成"已验证可用"；更糟的是新建扫描向导的 `configured` 读的正是
`verified`，它会把这个 provider 当成可用模型列出来，用户选中后在扫描跑到
一半时认证失败。

"填了 key"与"key 能用"是两件事 —— `data/providers.ts` 早就写明过。
落地就是 `saveProviderAccount` 里的 `keyChanged` 判断。

### 跨页一致性：providers 从常量变成了投影

`data/providers.ts` 原本导出常量 `MOCK_PROVIDERS`，`useProviders()` 直接返回它。
设置页可编辑之后那是个 bug：改完设置，向导读的还是写死的常量 ——
而该文件顶部自己写着"配置完成后回到这里，新配置的模型会自动出现"。

现在投影的唯一来源是 `settings-store` 里的账号列表（`projectToProviderConfigs`）。
**实测验证**（用站内路由跳转，不是整页刷新 —— 整页刷新会重置内存态 store）：
在设置里改掉某 provider 的 key，向导第 3 步立刻把它从可选列表移到
「尚未配置：凭据已更改，需要重新验证」。

> ⚠️ 投影里**不含 apiKey**。向导只需要知道"能不能用"，凭据不该流进它的数据结构 ——
> 它会渲染、可能被截图、被打印。`ProviderAccount`（有凭据）与
> `ProviderConfig`（给消费者看）的分工见 `data/settings.ts`。

### 令牌明文只出现一次

创建后展示完整值是用户**唯一**的机会，之后列表只留前缀
（`svx_ab12…`，前 8 位）。类型上就分开：`ApiToken` 没有 `value` 字段，
完整值只在 `CreatedToken.plaintext` 里出现一次、不进入 store。

> **这里踩过一个死锁**：最初把"关闭"按钮设计成复制成功前禁用，
> 意图是防误关。但实测中剪贴板写入失败时（非 HTTPS、权限被拒、沙箱 iframe
> —— 真实环境都会发生），关闭按钮永远点不了，**面板无法关闭**。
> 把唯一的出口锁死，比"可能误关"严重得多。
> 改成**二次确认**：关闭时若还没确认保存过，先就地追问一句。
> 保护还在，但永远留一条出路。
>
> 同类教训：复制失败必须**告诉用户怎么办**（手动选中复制），
> 而不是静默无反应让他反复点。

### mock 边界必须写在页面上

**任务 7 之后这条规则基本退役了 —— 但退役得不彻底，剩下的部分更要说清楚。**

绝大多数数据现在都来自后端，所以"刷新会回初始值"不再成立。例外是
**设置页的沙箱与通知两块**：契约 §9 里它们仍排在未交付的后端任务里，
store 保持内存态并**在面板上显式标注**（`BACKEND_PENDING` / `BACKEND_PENDING_NOTE`）。

不给它们编一个假的后端行为，也不悄悄让人以为保存住了 ——
与 TopStatusBar 上"用量统计未接入"是同一条原则：
**不伪造不存在的持久化能力。**
（状态条那一栏原来写着 `184.3k / 1M · 18%`，那是编的，
而它会被用户当成"这个月还能跑多少"的依据。）

> 顺带在上面说明了**凭据不落浏览器存储**。这不只是安慰话，它同时解释了
> 为什么"刷新就没了"**不该**用 localStorage 去修：浏览器存储同源的任何脚本
> 都能读，把 API key 放进去等于用一个便利性缺陷换一个真正的安全缺陷。
> 正确做法是提交给服务端 —— 任务 7 之后，provider 凭据与令牌**确实**是这么做的。

### 展开的表单必须自己进入视野（`useRevealOnExpand`）

设置页的编辑器都是**行内展开**的。实测：视口 1018px 时，展开后整行底边
落在 **1170px**，保存按钮正好在折叠线以下 67px —— 用户点「编辑」却看不到
保存按钮。对一个承诺"保存状态可信"的页面，主操作够不着是很糟的开场。

只滚"超出量"（`bottom - innerHeight`，没超出就不动），不用 `scrollIntoView`：
`block:'end'` 会让本来就完整的表单也跳一下；`block:'nearest'` 在元素高于视口时
对齐顶边，反而把保存按钮推出屏幕。

> **这里踩了一个真坑，值得单独记**：第一版用 `behavior: 'smooth'`，
> 结果**完全没滚动**。埋点确认 effect 跑了、overflow 也算对了 152，
> 但 scrollY 始终是 0。隔离验证：
>
> ```
> window.scrollBy({ top: 176, behavior: 'smooth' }) → scrollY 0    （没动）
> window.scrollBy({ top: 176, behavior: 'auto' })   → scrollY 176  （正常）
> ```
>
> **平滑滚动会在某些环境里静默 no-op**（无头浏览器、后台标签页、部分 webview
> —— 只要合成器没有帧在跑，平滑动画就不推进）。而它失败的方式最坏：
> 不报错、不滚动，用户只觉得"保存按钮还是看不见"。
>
> 结论：**把内容带进视野是功能性动作，不是装饰**，功能性动作不能依赖
> 动画能不能播出来。这是 §5「动效服务于信息，不服务于装饰」的延伸 ——
> 当动画可能挡住功能时，去掉动画。代价是失去一点平滑感，换可预期。

## 13. 开发环境的一个坑：dev server 白屏（务必先看这里）

任务 7 期间遇到一次**整页白屏**：`#root` 为空、刷新无效、控制台拿不到
有用信息。当时一度怀疑是刚写的代码有运行时错误。

**结论：不是代码问题。** 排查记录留在这里，避免下次重新查一遍：

| 观察                                         | 结论                                 |
| -------------------------------------------- | ------------------------------------ |
| `npm run typecheck` / `lint` / `build` 全绿  | 编译层面没问题                       |
| **`vite preview` 跑生产构建 → 页面完全正常** | **产物是对的，问题在 dev server**    |
| dev server 日志里有一次中间态的解析错误      | 文件被我改坏的那一瞬间被 Vite 编译过 |
| 重启 dev server → 恢复正常                   | 确认是陈旧的 HMR/模块图状态          |

**判断顺序（照这个走，别先改代码）**：

1. `npm run build` 是否通过 → 通过说明是工具层问题，不是应用逻辑；
2. 用 `npx vite preview` 打开**生产构建** → 正常就坐实了；
3. 重启 dev server。

> 教训不在"Vite 有 bug"，而在于：**白屏不等于代码坏了**。
> 编译通过 + 生产构建正常，这两条足以把怀疑对象从应用代码移到工具状态。
> 当时我花了若干轮在代码里找运行时异常，如果先跑一次 `vite preview`，
> 三十秒就能定位。

## 14. 产品首页（任务 8）

### 为什么补这一页

任务 0–7 铺完六个功能页后，根路径直接 `redirect` 到 `/overview`。
后果是：**第一次打开产品的人落在一个看板上，
而没有任何地方说过"Suvex 是什么"。**
（当时那个看板还塞满演示数据；任务 7 把它换成真实数据之后，
新用户落到的是一片"还没有扫描记录"—— 首页的必要性只增不减。）

对一个要交付给渗透测试人员、还要由他们决定"是否让这个 agent 对真实目标发包"
的工具，这是顺序错了：应该先知道它是什么、能自己做什么、边界在哪，
再去看它的数据。所以根路径改成一个独立的产品首页。

### 独立布局，不套 AppShell

首页**没有侧栏、状态条、移动底栏**。理由：首屏只有一个任务 ——
讲清这是什么，然后给一条进控制台的路。带上六个导航入口的侧栏会立刻分散注意力。

顺带解决一个技术问题：站内 `AppShell` 挂着 `AgentField`（WebGL），
首页有自己的 `HeroBackdrop` —— 不套壳就天然避免了"两个 WebGL 背景叠在同一视口"
（§5 明确禁止，会在集显上掉帧）。

### Hero 的构成

| 层      | 内容                        | 职责                             |
| ------- | --------------------------- | -------------------------------- |
| 底色    | `canvas` 近黑               | 最深处                           |
| Threads | WebGL 线场，`opacity: 0.70` | "数据正在通过"。唯一持续运动     |
| 压角    | 径向渐变                    | 中心留亮给标题，四角压暗         |
| 文案层  | 状态行 / 标题 / 说明 / CTA  | 信息                             |

（原「DotGrid 光标跟随点阵（仅大屏）」一层已移除，原因见 §5 与
`DEPENDENCIES.md` §4.3。）

比站内的 `AgentField` 强度高一档（0.70 vs 0.55）：站内它只是氛围，
首屏要它承担"一眼记住"。但仍不给满 —— 满强度的紫罗兰波浪读起来是
"AI 产品落地页模板"，而我们要的是"一个正在跑的工具"（§5 那条通则）。

### 一屏只有一个高饱和主色块

页面里 violet 的实心填充只有**一个**（主 CTA「进入控制台」），
其余都是描边按钮、文字链接、1px 线。这是 §2 的自律条款
"主色不许铺大面积，一屏覆盖 < 5%"的直接执行。

### 文案：五条自我约束

见 `LandingPage.tsx` 头部注释。核心是**说行为、不说形容词**，
且**把限制写在页面上**（需要对目标有授权 / 写入类验证可能改文件 /
需要自己配模型 key）—— 这些不是免责声明，是能否被信任的核心信息。

### 结构：不用等大卡片阵列

"它自己做的一个循环"用的是**带连接线的纵向序列**，不是四张等大卡片。
因为四步确实是顺序关系（不收集信息就无从判断，不判断就无从验证），
连接线本身携带信息 —— 而 §9 禁止的正是"等大 = 没有做取舍"。

> **D1–D4 值得单独强调**：同一个动效我连改三版都没修好，
> 前三版都在"补兜底"，而结论是**兜底补不出来** ——
> 只要"显示文字"依赖某个调度器推进，就存在永远不显示的路径。
> 最终换掉设计，失败模式才真正消失。
> 通则已写进 §5.1 的"动效不能挡住功能"。

> **D7 是一条方法论教训，比前面几条都重要**：
> 我一开始把"改用纯 CSS"当成了安全性的**原因**，并写进了文档和代码注释。
> 复核时做了一次对照实验（唯一变量 = 动画动的是哪个属性，环境 = 隐藏标签页）：
>
> | 动画只动    | 计算 opacity | 是否可见   |
> | ----------- | ------------ | ---------- |
> | `opacity`   | `0`          | **不可见** |
> | `transform` | `1`          | 可见       |
>
> 结论：**CSS 并不免疫调度器挂起**（`document.timeline.currentTime` 恒为 0，
> 动画停在 from 态且 `playState` 仍报 `running` —— 一个很容易骗过自己的状态）。
> 真正起作用的是"只动 transform"这一条，和用 CSS 还是 JS 无关。
>
> 教训：**改完之后要回头质疑"我为什么会认为它安全"，
> 而不只是验证"它现在显示正常"。**
> 当时的验证方法（读 computed style 看 opacity 是否为 1）恰好**无法区分**
> 这两种解释 —— 因为改动同时引入了"默认可见"和"只动 transform"两个因素，
> 而我只测了结果，没有隔离变量。**结论必须由对照实验支撑，不能由"改完就好了"支撑。**
> 循着错因继续往下走，会写出"以后一律用 CSS 就安全了"这种错误规范。

> **D6 是一条独立教训**：Tailwind 对**不存在的工具类不报错**，
> 只是什么都不做。所以 `animate-xxx` 拼错 = 一个静默失效的动效。
> 检查方式已写进 §5.1 的清单；本轮用一次性脚本对着 `tailwind.config.js`
> 核对了全部 11 个 `animate-*` 用法，全部有对应 token。

> **D8 说明这条纪律当时并没有被执行到位**：
> 我在 §5.1 里写下了"内容不许用不可见的初态"，

> 可见性不再依赖动画是否推进。

> **D9 再次印证 D7 的教训**：我原本在注释里断言"终态是 `transform: none`，
> 所以没有包含块" —— 那是**推理**，不是实测。

### 关于本轮验证方法的一条总则

**先写预期值，再测。** 本轮的 D10 是最好例子：
我预期"流转一条 → 1 个徽标落定"，实测是 **2**。
如果我当时只是"看一眼有没有闪"，这个差异就会被忽略；
而顺着它追下去，确认了「同一条漏洞在列表和抽屉各渲染一次」这个架构事实。

没有预期，就没有差异；没有差异，就没有确认 —— 只剩"看起来没问题"。
